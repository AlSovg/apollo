# Apollo — платформа интеллектуального управления оповещениями

Зонтичный слой над системами мониторинга (Zabbix, SolarWinds, Prometheus):
принимает потоки событий, нормализует их к каноническому виду, дедуплицирует,
маршрутизирует по подпискам и доставляет уведомления — веб-инбокс, email,
TrueConf. К инцидентам пишутся человекочитаемые сводки. Кейс IT CAMP 2026, заказчик — Газпром нефть.

## Что умеет

- **Приём** — `POST /api/v1/ingest/{source}`: один INSERT и ответ 202, никакого
  разбора на приёме. Токен на источник, опциональная HMAC-подпись, ограничение
  частоты на источник, лимит тела.
- **Нормализация** — адаптеры Zabbix 7 / SolarWinds / Prometheus Alertmanager
  плюс декларативный маппинг для новых источников: подключение без строчки кода
  в ядре.
- **Дедупликация** — события склеиваются в инциденты по отпечатку
  `(source, external_key)`; на нагрузочном прогоне поток сжимается в 12–20 раз.
- **Маршрутизация** — темы с правилами отбора (источник, критичность, группы
  объектов), подписки прямые и по ролям, глушение на время.
- **Доставка** — веб-инбокс, email, TrueConf; ретраи с расписанием, история
  доставки по каждому уведомлению. На стенде TrueConf отключён (ВМ
  недоступна), его роль играет email через `mailpit`: письма видны в
  http://localhost:8025. Уведомления отключённого канала штатно уходят в
  `failed`, как email без `SMTP_HOST`.
- **Сводки** — два провайдера (`LLM_PROVIDER`): `template` — детерминированный
  шаблон, в который подставляются поля и метрики события Zabbix/SolarWinds
  (на стенде по умолчанию), и `openai` — Qwen3-14B на выделенной ВМ (vLLM,
  OpenAI-совместимый API). Недоступность модели не влияет на доставку.
- **Администрирование** — реестр источников с кнопкой «Тест» (разбор payload
  без записи), темы, пользователи (LDAP + локальные), журнал аудита, дашборд
  платформы с задержками конвейера против нормативов.

## Архитектура

```
POST /ingest/{source} ──► raw_events (append-only)
        │  normalizer (FOR UPDATE SKIP LOCKED)
        ▼
   incidents ◄─ дедупликация ─ monitored_objects
        │  router: темы → эффективные подписчики
        ▼
  notifications (pending) ──► delivery workers ──► инбокс / email / TrueConf
        │
        └─ llm worker ──► сводка инцидента
```

Очередь — таблицы PostgreSQL с `FOR UPDATE SKIP LOCKED`; брокеров сообщений
в контуре нет намеренно. Вся логика нормализации и критичности —
детерминированный код, LLM используется только для сводок.

| Слой | Стек |
|---|---|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, Pydantic v2 |
| БД | PostgreSQL 16, партиционирование событий по месяцам |
| Frontend | Nuxt 3 (`ssr: false`), Pinia, типы из OpenAPI |
| Развёртывание | Docker Compose, nginx-unprivileged, строгая CSP |
| Сводки | шаблонный генератор (стенд) или vLLM + Qwen3-14B-AWQ, OpenAI-совместимый endpoint |

## Быстрый старт

```bash
cp .env.example .env        # заполнить секреты, включая INGEST_TOKEN_*
cd deploy
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
docker compose exec backend alembic upgrade head              # схема и справочники
docker compose exec backend python -m app.cli sync-tokens     # токены источников из .env
docker compose exec backend python -m app.cli create-admin breakglass --password 'Demo-stand-2026'
docker compose exec backend python -m app.seed                # каталог тем и роли групп
docker compose exec backend python -m app.demo_seed --password 'Demo-stand-2026'
curl localhost/health       # 200 — живой
```

Интерфейс — http://localhost. Учётные записи — в разделе
[«Учётные записи стенда»](#учётные-записи-стенда) ниже.

`--password` у обеих команд задаёт известный пароль вместо случайного: он
нужен, чтобы креды совпали с написанным здесь. Без флага `create-admin` и
`demo_seed` генерируют пароль и печатают его один раз — так и надо делать
везде, кроме разборного стенда.

`app.seed` заводит только каталог тем, событий не создаёт — после чистого
`up` инбокс пуст. `app.demo_seed` доводит стенд до состояния «есть что
показать»: четыре локальных пользователя с разными ролями и каналами
доставки, добровольные подписки и набор инцидентов Zabbix/SolarWinds разной
давности и критичности. Инциденты не пишутся в таблицы напрямую, а проходят
теми же `process_batch`/`route_batch`, что крутят воркеры. Пароли печатаются
один раз при создании; `--reset` возвращает стенд к чистому состоянию.

`.env.example` из коробки рассчитан на dev-оверлей и не требует внешних
адресов: сводки строит шаблон (`LLM_PROVIDER=template`), почту ловит `mailpit`
(`SMTP_HOST=mailpit`, интерфейс — http://localhost:8025), каталог заменён
OpenLDAP-моком. `TRUECONF_BASE_URL` пуст, поэтому уведомления канала TrueConf
уходят в `failed`, остальной конвейер не страдает.

По умолчанию поднимаются по две реплики `backend` и `normalizer`
(`deploy.replicas`); nginx распределяет запросы по репликам, заголовок ответа
`X-Upstream-Addr` показывает, какая обслужила. Число реплик меняется на лету:
`docker compose up -d --scale backend=3`. Архитектура и ограничения —
[docs/architecture-scaling.md](docs/architecture-scaling.md).

`.env.example` по умолчанию ставит `AUTH_PROVIDER=local` — этого достаточно
для первого запуска и локальной разработки. Ветка `ldap` проверяется только
против локального мока (см. [«Учётные записи стенда»](#учётные-записи-стенда)
ниже) — удалённая ВМ с боевым Samba AD DC сейчас недоступна, переключение на
неё было бы сменой переменных окружения без пересборки образов, но
демонстрировать сейчас нечем.

Подробности, продовый контур и отличия dev-оверлея —
[docs/deployment.md](docs/deployment.md).

## Эмулятор источников

Доступа к ВМ Zabbix и SolarWinds по SSH сейчас нет (`docs/integration-runbook.md`
§4), поэтому «генератор событий», который по архитектуре стоит на ВМ №1 и №2
(`AGENTS.md` §3), вынесен в контейнер `simulator`. Он шлёт те же вебхуки на
`POST /api/v1/ingest/{source}`, что и боевые системы: те же поля, форматы
времени и заголовки аутентификации. Переключение на настоящий источник —
остановить сервис, код платформы при этом не меняется.

Токен берётся из `INGEST_TOKEN_ZABBIX` / `INGEST_TOKEN_SOLARWINDS` — тех же
переменных, что применяет `app.cli sync-tokens` в реестр источников. Отдельной
настройки эмулятору не нужно, достаточно поднять его с профилем `demo`:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  --profile demo up -d simulator
```

Профиль `demo` означает, что обычный `up` эмулятор не поднимает.

Работает в двух режимах одновременно. **Поток** — раз в `SIM_INTERVAL_S`
(25 секунд по умолчанию, ~2-3 события в минуту) открывает новую проблему,
повторяет открытую или закрывает её; стенд выглядит живым, инбокс за час
показа не заплывает. **Сценарии** — готовый сюжет целиком по HTTP:

```bash
curl localhost:18082/scenarios              # список с пояснениями
curl -X POST localhost:18082/scenario/scada-down
curl localhost:18082/state                  # отправлено, принято, открытые проблемы
curl -X POST localhost:18082/pause          # /resume — вернуть поток
```

| Сценарий | Что показывает |
|---|---|
| `scada-down` | АСУ ТП Приобье: узел недоступен + перегрев соседнего → темы `scada-asu`, `critical-any` |
| `network-msk` | Магистраль Москва: узел лёг, на соседнем потери пакетов → тема `network-core` |
| `db-replication` | БД prod: остановлена репликация, теги `sla`+`prod` → `prod-db`, `sla-watch`, `critical-any` |
| `web-degradation` | Веб prod: рост отклика на сервере и балансировщике → тема `web-prod` ловит оба источника |
| `noise` | Пять событий уровня Information со stage — шум, который темы обязаны отсечь |
| `storm` | 50 событий подряд, большинство повторы — дедупликация в работе |
| `resolve-all` | Закрыть все проблемы, открытые эмулятором |

Парк объектов Zabbix тот же, что у `app.demo_seed` (`gpn-scada-07`,
`gpn-db-prod-02` и далее), поэтому события ложатся в уже существующие темы и
не плодят вторую инфраструктуру на дашборде. Узлы SolarWinds поток и сценарии
берут из пула площадок (`gpn-net-msk-07`, `gpn-net-nsk-23`, …): ключ
дедупликации там — пара «узел + алерт», и на шести постоянных именах источник
после первого прогона перестал бы порождать уведомления вообще. События идут
как боевые — попадают в инциденты, порождают уведомления и доходят до инбокса
и в почту (mailpit).

Нагрузочный прогон — это по-прежнему `tools/load_generator.py`: там залп,
перцентили и отчёт, здесь ровный фон и управляемый показ.

## Учётные записи стенда

> Всё ниже — реквизиты разборного демонстрационного стенда, поднятого под
> защиту кейса. Учётки локального мока (домен `apollo.test`, сервис `ldap`
> из dev-оверлея) существуют только для проверки ветки `ldap` и гасятся
> вместе со стендом. В продуктивном контуре
> секретов в репозитории нет: `.env` не коммитится, пароли задаются при
> развёртывании, а `create-admin` и `demo_seed` без `--password` печатают
> сгенерированный пароль один раз.

### Без AD — `AUTH_PROVIDER=local`

Ветка первого запуска: каталог не нужен, учётки заводят команды из «Быстрого
старта». Пароль — тот, что передан в `--password` (в примерах выше
`Demo-stand-2026`).

| Логин | Роль | Что показывает |
|---|---|---|
| `breakglass` | admin | админка: темы, источники, пользователи, аудит, дашборд платформы |
| `duty.engineer` | engineer | инбокс дежурного, обязательные подписки + добровольная с email |
| `shift.lead` | engineer | второй дежурный: добровольная подписка с каналом email (TrueConf временно отключён) |
| `noc.viewer` | viewer | наблюдатель сети: обязательная подписка `network-core` |
| `service.owner` | viewer | владелец сервиса: узкая подписка только на `web-prod` |

### С каталогом — `AUTH_PROVIDER=ldap`

Боевой AD заказчика сейчас недоступен (удалённая ВМ с Samba AD DC отключена,
см. `docs/deployment.md`) — ветка `ldap` проверяется только против локального
мока каталога: сервис `ldap` (`osixia/openldap`) из dev-оверлея,
`deploy/ldap/01-structure.ldif`. Учётки заводятся в платформе сами при первом
входе, роли приезжают из групп каталога через сопоставления из `app.seed` —
те же имена групп, что и у боевого AD, поэтому маппинг ролей не менялся.

| Логин | Группа каталога | Роль | Пароль | Что показывает |
|---|---|---|---|---|
| `admin.ops` | platform-admins | admin | `admin-pass` | админка под учёткой каталога |
| `noc.duty` | noc-engineers | engineer | `duty-pass` | инбокс дежурного смены |
| `eng.network` | noc-engineers | engineer | `eng-pass` | второй инженер сети |
| `biz.owner` | service-owners | viewer | `viewer-pass` | наблюдатель, владелец сервиса |
| `no.groups` | — | без ролей | `nobody-pass` | вход есть, доступа к данным нет — проверка RBAC |

У каждой учётки мока есть атрибут `mail` (`<логин>@apollo.test`), поэтому
email-доставка работает и для доменных пользователей — письма оседают в
mailpit. Атрибута `ipPhone` нет, TrueConf на стенде отключён.

`app.demo_seed` назначает доменным учёткам (`DIRECTORY_USERS` в
`backend/app/demo_seed.py`: `noc.duty`, `eng.network`, `biz.owner`) подписки с
`origin=assigned` на канал email. Учётка должна уже существовать в платформе,
то есть один раз войти или дождаться синхронизации каталога, иначе шаг
пропускает её как «не найден». Мок не даёт ролям обязательных подписок с
email, только `web`, так что для проверки письма нужен именно этот шаг.

**Важно:** пока каталог доступен, локальные учётки (`breakglass` и демо-
пользователи) войти не могут — при `AUTH_PROVIDER=ldap` вход идёт только
через каталог. Локальный провайдер включается как аварийный, если каталог
лёг (FR-IDM-7). Это не дефект, а требование: отказ каталога не должен
запирать вход в саму платформу.

## Проверки качества

```bash
cd backend
ruff check && mypy && pytest    # линт, строгая типизация, ~340 тестов
```

Тесты идут против настоящего PostgreSQL (dev-оверлей публикует порт 55432)
и моков внешних систем — LDAP и LLM повторяют реальные контракты. Шаблонный
генератор сводок (`test_llm_template.py`) — чистая функция, БД и сеть ему не
нужны. Тесты
канала TrueConf (`test_trueconf_channel.py`) сами пропускаются, если мок
недоступен (сейчас закомментирован в оверлее) — тот же паттерн, что и
у остального конвейера при отключённом канале.
