# Подключение боевых источников

Схема на время разработки: apollo работает на рабочей машине, Zabbix 7 и
SolarWinds Observability Self-Hosted — на отдельных ВМ. Прямой путь к apollo
у них отсутствует, поэтому события идут через обратный SSH-туннель.

```
Zabbix 7 (ВМ)  ──► 127.0.0.1:18080 ─┐
                                    ├─ обратный SSH-туннель ─► apollo :80 (локально)
SolarWinds (ВМ) ──► 127.0.0.1:18080 ┘
```

Порт `18080` поднимается на самой ВМ и слушает только петлю: наружу не
открывается ничего, менять `GatewayPorts` на сервере не требуется.

При переезде apollo на выделенную ВМ туннель убирается, а в настройках
источников меняется только URL — ни скрипт, ни шаблоны тел не трогаются.

## 1. Туннель

С рабочей машины, по одному окну на каждую ВМ:

```powershell
.\tools\tunnel.ps1 -VmHost <ip-zabbix> -User ubuntu -KeyFile ~\.ssh\key.pem
.\tools\tunnel.ps1 -VmHost <ip-solarwinds> -User admin -KeyFile ~\.ssh\key.pem
```

Скрипт проверяет, что локальный apollo отвечает, и переустанавливает
соединение после обрыва. Проверка со стороны ВМ:

```bash
curl http://127.0.0.1:18080/health
```

## 2. Токены источников

Токен выдаётся в админке: **Источники → «Токен»** (или «Токен + HMAC», если
нужна подпись). Значение показывается один раз. У каждого источника свой
токен — компрометация одного не открывает второй.

## 3. Zabbix 7

### Media type

**Alerts → Media types → Create media type**, тип **Webhook**, имя `Apollo`.
Скрипт — содержимое `zabbix7-webhook.js`.

Параметры (Parameters):

| Имя | Значение |
|---|---|
| `url` | `http://127.0.0.1:18080/api/v1/ingest/zabbix` |
| `token` | `{$APOLLO_TOKEN}` — заведите глобальный макрос типа **Secret text** |
| `hmac_secret` | `{$APOLLO_HMAC}` — только если выдавали «Токен + HMAC», иначе не добавляйте |
| `event_id` | `{EVENT.ID}` |
| `event_nseverity` | `{EVENT.NSEVERITY}` |
| `severity` | `{EVENT.SEVERITY}` |
| `status` | `{EVENT.STATUS}` |
| `event_value` | `{EVENT.VALUE}` |
| `date` | `{EVENT.DATE}` |
| `time` | `{EVENT.TIME}` |
| `recovery_date` | `{EVENT.RECOVERY.DATE}` |
| `recovery_time` | `{EVENT.RECOVERY.TIME}` |
| `host` | `{HOST.NAME}` |
| `host_technical_name` | `{HOST.HOST}` |
| `host_ip` | `{HOST.IP}` |
| `hostgroup` | `{TRIGGER.HOSTGROUP.NAME}` |
| `trigger_id` | `{TRIGGER.ID}` |
| `trigger_name` | `{TRIGGER.NAME}` |
| `trigger_expression` | `{TRIGGER.EXPRESSION}` |
| `message` | `{ALERT.MESSAGE}` |
| `item_lastvalue` | `{ITEM.LASTVALUE}` |
| `event_tags` | `{EVENT.TAGSJSON}` |

На вкладке **Options**: *Attempts* = 3, *Attempt interval* = 10s. Это и есть
защита от короткой недоступности apollo — перезапуск бэкенда не теряет событий.

Отдельное время восстановления (`recovery_date`/`recovery_time`) нужно, чтобы
закрытие инцидента не проставлялось задним числом временем проблемы.

Важно, что в поле `event_id` стоит именно `{EVENT.ID}`, а не
`{EVENT.RECOVERY.ID}`: в recovery-операции Zabbix подставляет сюда номер
исходной проблемы, и закрытие склеивается с тем же инцидентом. С номером
восстановительного события вместо закрытия создался бы новый инцидент.

### Пользователь и действие

1. Пользователю, от имени которого идёт отправка, добавьте медиа типа `Apollo`
   (поле *Send to* заполните любым непустым значением — скрипт его не читает).
2. **Alerts → Actions → Trigger actions → Create action**, условие — по вкусу
   (например, «Trigger severity >= Warning»).
3. **Operations**: отправка через `Apollo`.
4. **Recovery operations**: та же отправка через `Apollo` — без неё инциденты
   не будут закрываться.

### Альтернатива: Connectors

Zabbix 7 умеет потоковый экспорт событий (**Administration → General →
Connectors**) со своей очередью и ретраями. Путь заманчивый, но коннектор шлёт
**батчи** — массив событий в одном запросе, а нормализатор рассчитан на одно
событие в теле. Понадобится доработка разбора батча, поэтому этот вариант —
после того, как заработает обычный.

## 4. SolarWinds Observability Self-Hosted

Механика прежней Orion Platform: **Alerts → Manage Alerts → выбрать алерт →
Trigger Actions → Add Action → Send a GET or POST Request to a Web Server**.

- URL: `http://127.0.0.1:18080/api/v1/ingest/solarwinds`
- Метод: **POST**, тело — содержимое `solarwinds-alert-body.json`
- Заголовки: `Content-Type: application/json`, `X-Webhook-Token: <токен>`

На вкладке **Reset Actions** — такое же действие с телом
`solarwinds-reset-body.json` (отличается `eventType` и временем).

Переменные в шаблонах подставляются под конкретный алерт: если алерт построен
не на узлах, а на интерфейсах или приложениях, `${N=SwisEntity;M=Caption}`
вернёт имя соответствующей сущности — это нормально, adapter кладёт её в объект
мониторинга. Свойство `group` в шаблоне указано примером
(`CustomProperties.Department`) — замените на то, что реально заполнено, или
удалите строку.

### Что нужно проверить в первую очередь

Формат reset-события в адаптере — **непроверенная гипотеза**: закрытие алерта
распознаётся по `eventType` из набора `reset`/`resolved`/`cleared`/`recovery`.
Живого закрытия на стенде не наблюдали. Первое настоящее срабатывание Reset
Action либо подтверждает гипотезу, либо мы правим адаптер по факту. Это
единственное место в конвейере, где остаётся допущение.

## 5. Проверка до боевого включения

Не включайте отправку сразу на все алерты. Порядок:

1. Снимите с каждой системы по одному настоящему событию — проблему и закрытие.
2. Вставьте тело в **Источники → «Тест»** в админке apollo: payload
   разбирается и показывается результат, в базу ничего не пишется.
3. Убедитесь, что определились объект, правило, критичность и вид события
   (проблема/восстановление).
4. Только после этого включайте действие на боевые триггеры.

## 6. Частые причины, по которым события не доходят

| Симптом | Где смотреть |
|---|---|
| Zabbix пишет «apollo вернул 401» | токен не совпадает с выданным; при «Токен + HMAC» не задан `hmac_secret` |
| «apollo вернул 403» | у источника заполнен список разрешённых адресов, а через туннель запрос приходит с `127.0.0.1` |
| Ответ 202, но инцидента нет | событие лежит в `raw_events` с `process_error` — смотрите ошибку разбора в админке |
| Инциденты не закрываются | не настроена recovery-операция (Zabbix) или Reset Action (SolarWinds) |
| Время инцидента смещено на часы | часовой пояс источника в реестре не совпадает с временем на ВМ; проверьте NTP |
| Дубли инцидентов | у события меняется `event_id`/`ObjectID` между повторами — смотрите ключ склейки в карточке |
