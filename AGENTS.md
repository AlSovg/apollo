## 1. Что мы строим

Единый «зонтичный» слой над несколькими системами мониторинга. Он принимает
события от Zabbix и SolarWinds, приводит их к общему формату, схлопывает
дубликаты, определяет **кому** это событие важно, и доставляет уведомление
через выбранные каналы. LLM превращает технический алерт в человекочитаемую
сводку.

Кейс IT CAMP 2026, заказчик — **Газпром нефть**. Формат — рабочий прототип
за 1–2 недели.

### Проблема, которую решаем

Цифры заказчика — не наши оценки, а исходные данные кейса:

| Показатель | Значение |
|---|---|
| Событий в сутки | 5400 от 7 систем мониторинга |
| Уровень шума | 65 % уведомлений закрываются без реакции за первые 2 минуты |
| Незамеченный простой критичного сервиса | 14 минут в среднем |
| Цена одного такого инцидента | ~3,2 млн ₽ упущенной выгоды |
| Ручная обработка алертов силами L1 | 48 человеко-часов в сутки |

Сотрудник отвечает сразу за несколько сервисов, единого механизма подписок нет,
смена состава получателей требует правки настроек в каждой системе отдельно.
В результате канал игнорируется, и о реальном сбое узнают поздно.

### Периметр пилота

Блок разведки и добычи, 4 филиала, 87 пользователей. Источники в пилоте —
**Zabbix** (мониторинг АСУ ТП) и **SolarWinds** (сетевое оборудование).
Тираж на всю Группу — второй этап после подтверждения метрик.

### Целевые бизнес-показатели

MTTR не более 20 минут, доля ложных срабатываний до 5 %, минус 60 % ручной
фильтрации у дежурной смены NOC, экономия ФОТ техподдержки 1,1 млн ₽ в квартал.
Расчёт — в `docs/economics.md`.

### Ключевой принцип

**Работающий сквозной путь важнее богатого функционала.** Одно событие должно
пройти все шаги — приём → нормализация → дедупликация → маршрутизация →
доставка → инбокс дежурного — раньше, чем мы начнём добавлять фичи.

## 2. Стек и обоснование выбора

| Слой | Технология | Почему именно так |
|---|---|---|
| Фронтенд | Nuxt 3, `ssr: false` | Основной стек команды. Собирается в статику — в контуре не остаётся Node-процесса |
| Раздача статики | nginx | Единственный процесс фронта в проде, TLS терминируется здесь |
| Бэкенд | FastAPI, Python 3.12 | Малое дерево зависимостей (~40–60 против ~800 у npm), зеркалируемый PyPI, пакеты есть в репозиториях Astra Linux |
| ORM / миграции | SQLAlchemy 2.0 + Alembic | Параметризованные запросы по умолчанию, версионирование схемы |
| Валидация | Pydantic v2 | Строгая схема на границе, отказ от неизвестных полей |
| БД | PostgreSQL 16 | Партиционирование, JSONB, `SKIP LOCKED` для очереди |
| Очередь | Таблица в PostgreSQL + `FOR UPDATE SKIP LOCKED` | Ноль дополнительных компонентов — меньше поверхность атаки. На потоке десятков событий в минуту с запасом хватает |
| LLM | Локальная модель, OpenAI-совместимый endpoint | Данные не покидают контур |
| Упаковка | Docker Compose | Бэк, фронт и БД в контейнерах |

**Стека «без уязвимостей» не существует** — есть стек с управляемой поверхностью
атаки. Выбор выше сделан именно по этому критерию: минимум компонентов, offline-
сборка из зеркала, воспроизводимость, SBOM.

### Чего в проекте нет и не должно появиться

- Kafka, NATS, RabbitMQ — очередь живёт в PostgreSQL
- Redis — состояние живёт в PostgreSQL
- SSR-слой на Node в продуктивном контуре
- Любые CDN, внешние шрифты, внешние иконочные пакеты — всё локально
- Внешние LLM-API — модель локальная

### Импортозамещение

Условие кейса: решение должно использовать отечественные программные продукты
либо предусматривать возможность их использования. Ни один компонент стека
этому не препятствует:

| Компонент | Замещение | Что требуется |
|---|---|---|
| PostgreSQL 16 | **Postgres Pro Standard/Enterprise** — в реестре российского ПО | Смена образа, схема совместима |
| ОС хостов и базовые образы | **Astra Linux Special Edition** или **РЕД ОС** | Python, nginx, PostgreSQL есть в штатных репозиториях |
| Python, FastAPI, nginx, Nuxt | Свободное ПО, замещения не требует | Сборка из внутреннего зеркала PyPI и npm, без обращений наружу |
| Языковая модель | Российские открытые модели (например, семейства GigaChat/YandexGPT в self-hosted-варианте или открытые модели с дообучением) | OpenAI-совместимый endpoint, код не меняется |
| Docker | **Podman** при запрете Docker | Compose-файл совместим |

Само решение — внутренняя разработка, пригодная к регистрации в реестре
российского ПО. Требование «использование готовых рыночных моделей исключено
политикой ИБ (запрет передачи данных во внешние облака)» соблюдено буквально:
модель работает внутри контура.

## 3. Инфраструктура: четыре виртуалки

| # | Роль | Что стоит | Docker |
|---|---|---|---|
| 1 | Источник | Zabbix Server 7.0 LTS, Ubuntu 24.04, `90.156.212.194` + генератор событий | нет |
| 2 | Источник | SolarWinds HCO, Windows Server, `83.166.251.15` + генератор событий | нет |
| 3 | **Приложение** | nginx + статика фронта, FastAPI-бэкенд, PostgreSQL 16 | **да** |
| 4 | LLM | Локальная модель (OpenAI-совместимый API) | нет |

Источники сами шлют вебхуки на ВМ №3. Реквизиты доступа и текущее состояние
стендов — в файле `local/ФАЙЛИК ДЛЯ САШИ.md`.

**Внешние системы, которых на стенде нет.** TrueConf Server и LDAP/AD в кейсе
обязательны, но доступа к боевым нет. Оба адаптера пишутся полностью,
по документации протоколов, и проверяются против локальных подстановок:
OpenLDAP в контейнере и мок-сервер TrueConf, отвечающий по контракту его API.
Переключение на боевой сервер — смена переменных окружения, код не меняется.
Заглушка, которая пишет в лог и ничего не делает, требованию кейса не отвечает.

**Отказоустойчивость.** Событие считается принятым после записи в `raw_events` —
падение любого воркера не теряет его. Реплика PostgreSQL в потоковой репликации
предусмотрена архитектурно; в пилоте на одной ВМ она разворачивается по
готовности второй машины.

### Известные ограничения стендов

- На Ubuntu-ВМ порт 80 закрыт облачным Security Group, доступа к панели
  OpenStack нет. Наружу — только через SSH-туннель.
- Тестовые приёмники вебхуков на Windows-ВМ не переживают перезагрузку
  (запущены через Планировщик, а не как служба).
- Реального срабатывания алерта SolarWinds ещё не наблюдали — только ручная
  имитация. Формат `reset`-события не подтверждён.
- Пароль `Admin` в Zabbix — дефолтный `zabbix`, подлежит смене.

## 4. Доменная модель и глоссарий

Термины используются буквально в этих значениях — в коде, в API и в разговоре.

| Термин | Значение |
|---|---|
| **raw event** | Сырой вебхук как пришёл. Append-only, никогда не редактируется |
| **monitored object** | Наблюдаемый объект: хост, узел. Живёт дольше инцидентов |
| **incident** | Агрегат: одна строка = одна проблема. Единственная таблица, где бывает UPDATE |
| **incident event** | Запись в ленте инцидента: problem / resolved / ack / update |
| **fingerprint** | Ключ дедупликации: `sha256(source ‖ object ‖ rule)` |
| **topic** (тема) | Единица подписки. Каталог ведёт админ платформы. Внутри — правило отбора событий |
| **subscription** | Связь пользователя с темой. Три происхождения — см. ниже |
| **notification** | Экземпляр доставки конкретному пользователю по конкретному каналу |
| **ack** | Квитирование: дежурный взял инцидент в работу. Заложено, не реализовано |
| **escalation** | Передача выше по таймауту. Заложено, не реализовано |

### Три происхождения подписки

| Origin | Кто создаёт | Отписаться |
|---|---|---|
| `mandatory_role` | Вычисляется из привязки темы к роли | нет, только временное глушение |
| `assigned` | Админ платформы конкретному пользователю | нет |
| `self` | Пользователь сам в личном кабинете | да |

Эффективная подписка — объединение всех трёх. `mandatory_role` не хранится
строками, а вычисляется из ролей пользователя. Обязательная подписка всегда
побеждает глушение.

### Экран подписок

Один экран, две вкладки: **Обязательные** и **Доступные**. Фильтров по severity,
тегам и объектам в UI нет — вся сложность отбора спрятана в правило темы,
которое настраивает админ.

## 5. Персональные данные — жёсткое правило

Проект сознательно спроектирован так, чтобы не накапливать ПДн. Полностью выйти
из-под 152-ФЗ нельзя — связка «идентификатор сотрудника + канал доставки» уже
косвенные ПДн. Но объём сведён к минимуму: нет ФИО, нет спецкатегорий,
ИСПДн уходит на низший уровень защищённости.

**Храним:**
- `subject_id` — непрозрачный стабильный идентификатор из каталога (`objectGUID`)
- роли — кэш маппинга групп каталога во внутренние роли, с TTL
- подписки, журнал доставки — только по `subject_id`

**Не храним:**
- ФИО, должность, телефон
- email — резолвится адаптером каталога в момент отправки и не персистится
- отображаемое имя в UI — подтягивается по запросу, в БД не пишется

**В логи не попадают:** адреса доставки, тела уведомлений, payload событий.
Только `subject_id`, идентификатор уведомления и статус.

**Исключение на время MVP:** пока каталога нет, `LocalContactResolver` хранит
email в таблице `user_contacts`. Таблица помечена как содержащая ПДн и очищается
при переключении на LDAP. Это единственное место в схеме, где лежат контакты.

## 6. Архитектура обработки

```
Zabbix ─┐
        ├─► POST /api/v1/ingest/{source} ─► raw_events (append-only, 202 сразу)
SolarWinds ─┘                                   │
                                                ▼
                          normalizer worker (SKIP LOCKED)
                          ├─ адаптер источника → канонический вид
                          ├─ upsert monitored_objects
                          ├─ fingerprint → upsert incidents
                          └─ insert incident_events
                                                │
                                                ▼
                          router worker
                          ├─ подобрать темы по match_rule
                          ├─ развернуть в эффективных подписчиков
                          └─ создать notifications (pending)
                                                │
                          llm worker (сводка) ─►│ текст уведомления = сводка,
                                                │ ожидание до 15 с, затем
                                                │ исходное сообщение
                                    ┌───────────┴───────────┐
                                    ▼                       ▼
                             delivery: web            delivery: email
                             (инбокс)                 (SMTP)
```

### Правила, которые нельзя нарушать

1. **Эндпоинт приёма делает ровно один INSERT и отвечает 202 Accepted.** Никакого
   парсинга на приёме — иначе неожиданное поле уронит доставку события.
2. **`raw_events` не редактируется.** Исключение — служебные `processed_at` и
   `process_error`. Нормализованные слои — производные, их можно пересчитать.
3. **Запись инцидента только через `INSERT ... ON CONFLICT DO UPDATE`** по
   `(source, external_key)` — порядок доставки вебхуков не гарантирован.
4. **`incident_events` — только INSERT.** `incidents` отвечает «что сейчас»,
   `incident_events` — «как мы к этому пришли».
5. **Дедупликация:** повтор с тем же fingerprint в окне подавления (15 минут по
   умолчанию) инкрементит счётчик и НЕ порождает нового уведомления.

### Место ИИ в решении

Осознанная граница: **нормализация, дедупликация и определение критичности —
детерминированный код.** Языковая модель применяется в одном сценарии —
саммаризация инцидента.

Причина не в лени, и её нужно уметь объяснить на защите: нормализация обязана
быть воспроизводимой и объяснимой. Если инцидент попал не тому дежурному,
разбор должен упираться в конкретную строку правила, а не в «модель так
решила». Плюс модель на этом слое — это задержка и точка отказа на пути,
который обязан отработать за 5 секунд. Сводка — содержимое уведомления:
доставка ждёт её до 15 с и при таймауте отправляет исходное сообщение,
поэтому модель не становится точкой отказа доставки.

Прочие сценарии применения ИИ (семантическая нормализация, определение
дубликатов по смыслу, корреляция в цепочки с первопричиной, маршрутизация
на основе истории, рекомендации из базы знаний) проработаны как концепция
с обоснованием бизнес-ценности — раздел 3.8 `docs/tz.md`. В прототипе они
не реализуются.

## 7. Требования безопасности

Проект будет проходить ревью ИБ. Эти пункты — не пожелания.

**Контейнеры:** non-root пользователь, `read_only: true` на rootfs,
`no-new-privileges`, drop всех capabilities, ограничение ресурсов, healthcheck.

**Сеть:** TLS на nginx, HSTS, CSP без `unsafe-inline` и `unsafe-eval`, БД не
публикует порт наружу (при БД на отдельном узле — только на адрес закрытой
оверлейной сети, ADR-0006), между контейнерами — внутренняя сеть Compose.

**Аутентификация:** argon2id для паролей, JWT в `httpOnly Secure SameSite=Strict`
cookie, короткий access + refresh с ротацией, блокировка после N неудачных
попыток, аудит входов.

**Приём вебхуков:** статический токен + HMAC-подпись тела, rate limit,
ограничение размера тела, IP-allowlist адресов стендов.

**Данные:** параметризованные запросы только через ORM, строгая валидация
Pydantic с `extra="forbid"`, ретеншен `raw_events` 30 дней с дропом партиций.

**Аудит:** каждое изменение тем, ролей и подписок пишется в `audit_log`
с указанием актора, времени и прежнего значения. Действия администраторов
журналируются наравне с действиями пользователей.

**Жизненный цикл учётных записей:** учётка отключена или удалена в каталоге →
доступ закрыт, все подписки перестают порождать уведомления. Смена
должности → роли пересчитываются, обязательные подписки старой роли
отваливаются автоматически. Это прямое требование критерия ИБ, а не
дополнительная функция.

**Безопасность API для новых источников:** отдельный токен и HMAC-секрет
на каждый источник, отзыв без остановки остальных, ограничение частоты
и размера тела, IP-allowlist.

**Сборка:** зафиксированные версии зависимостей с хешами, `pip-audit` и `trivy`
в CI, генерация SBOM (CycloneDX), многостадийные Dockerfile.

## 8. Границы MVP

**Входит:**
- Приём вебхуков от обоих источников + фикстуры реальных payload
- Нормализация детерминированными адаптерами (никакого AI в этом слое)
- Дедупликация по fingerprint с окном подавления
- Каталог тем, три вида подписок, экран с двумя вкладками
- Веб-инбокс как основной канал, email как дублирующий
- **TrueConf** — обязательный канал по условиям кейса
- **LDAP/AD** — обязательная интеграция по условиям кейса, включая
  автоотключение подписок при увольнении и смене должности
- LLM-сводка инцидента
- Дашборд активных инцидентов
- **Административный дашборд платформы**: нагрузка, обработано событий, процент
  доставленных уведомлений, самые частые инциденты
- **Конфигурируемое подключение источника** — новый источник заводится записью
  в реестре и декларативным маппингом, а не правкой ядра

**Заложено структурно, не реализовано:**
- ack и эскалация по таймауту (поля в схеме есть)
- Маскирование данных перед LLM (флаг, по умолчанию выключен: модель локальная)
- Связывание одного физического сервера между Zabbix и SolarWinds

**Не входит:**
- Хранение таймсерий метрик (CPU/RAM по времени) — это отдельная задача и,
  вероятно, TimescaleDB. Для потока алертов оверкилл
- Семантическая дедупликация через LLM
- Мобильное приложение, push-уведомления

## 9. Как здесь принято работать

- Язык общения и документации — русский. Код, имена таблиц и полей — английский.
- Каждая новая интеграция источника — это **новый адаптер**, а не ветка `if`
  в общем коде. Появление третьего источника не должно трогать существующий.
- Прежде чем добавлять фичу, проверь, что сквозной путь всё ещё работает
  целиком: генератор → вебхук → инцидент → уведомление → инбокс.
- Нагрузочная проверка: тысяча событий из генератора. Что сломается первым —
  надо знать заранее, а не на защите.
- Секреты не коммитятся. `.env.example` — с плейсхолдерами.
