# Промпты сборки приложения

> Пошаговый план генерации. Каждый шаг — самостоятельный промпт: скопировать
> целиком в агента, дождаться результата, проверить критерии приёмки, идти дальше.
> Дата: 2026-08-10.

---

## Как этим пользоваться

**Общая преамбула.** Её нужно подставлять в начало каждого промпта — агент не
помнит предыдущие шаги:

```
Прочитай AGENTS.md, docs/tz.md и db/schema.sql в корне репозитория.
Это контекст проекта, соблюдай его требования буквально: стек, ограничения
по ПДн, правила обработки событий, требования ИБ.

Язык кода и имён — английский, комментарии и документация — русский.
Не добавляй зависимости сверх перечисленных в AGENTS.md.
Если требование в задаче противоречит AGENTS.md — остановись и скажи об этом,
не выбирай сам.
```

**Порядок нарушать нельзя.** Шаги 1–7 выстраивают сквозной путь: вебхук →
инцидент → уведомление → инбокс. Пока он не заработал целиком, шаги 8+ трогать
рано. Это прямое следствие ключевого принципа из `AGENTS.md`.

**После каждого шага:** прогнать тесты, проверить критерии приёмки, зафиксировать
коммит. Шаг, не прошедший приёмку, не считается сделанным — доделывать, а не
идти дальше.

**Карта шагов**

| # | Шаг | Результат |
|---|---|---|
| 0 | Каркас репозитория | Compose поднимается, `/health` отвечает |
| 1 | Схема и миграции | `alembic upgrade head` создаёт всю модель |
| 2 | Приём вебхуков | Реальный payload Zabbix лежит в `raw_events` |
| 3 | Адаптеры источников | Payload → канонический вид, покрыт тестами |

| 10 | Админ-дашборд платформы | Нагрузка, дедупликация, доставка, интеграции |

## Шаг 0 — каркас репозитория

```
Создай каркас проекта.

Структура:
  backend/          FastAPI, Python 3.12
    app/
      main.py           точка входа, роутеры, middleware
      config.py         настройки через pydantic-settings, только из ENV
      db.py             async engine, sessionmaker, зависимость get_session
      models/           SQLAlchemy 2.0, declarative, типизированные mapped_column

      adapters/         источники, identity, contacts, каналы, llm
      workers/          отдельные процессы-воркеры
    tests/
    alembic/
    pyproject.toml

  db/               schema.sql (уже есть), сиды
  deploy/           docker-compose.yml, Dockerfile'ы, nginx.conf
  .env.example

Требования:
- docker-compose поднимает postgres, backend, frontend(nginx). Порт БД наружу
  не публикуется.
- Оба Dockerfile многостадийные, финальный образ от non-root пользователя.
- В compose для сервисов приложения: read_only rootfs, no-new-privileges,
  cap_drop ALL, healthcheck, лимиты ресурсов.
- Эндпоинты GET /health (живость) и GET /health/ready (готовность: проверка
  соединения с БД).
- Конфигурация только через переменные окружения, без значений по умолчанию
  для секретов. .env.example с плейсхолдерами.
- Структурное логирование в JSON: request_id, метод, путь, статус, длительность.
  Тела запросов и ответов не логировать.
- Настроить ruff и mypy в strict-режиме, pytest с pytest-asyncio.

Приёмка:
  docker compose up -d поднимается без ошибок
  curl /health -> 200
  curl /health/ready -> 200
  ruff check и mypy проходят на пустом проекте

```

```
  Вызывать при старте приложения.

- Комментарии COMMENT ON из schema.sql сохранить — они объясняют неочевидные
  решения и должны дожить до продакшена.

Приёмка:
  alembic upgrade head на пустой БД проходит
  alembic downgrade base проходит без ошибок
  повторный upgrade head проходит (идемпотентность)
  \d+ incidents показывает все ограничения из schema.sql
```

## Шаг 2 — приём вебхуков

```
Реализуй эндпоинты приёма событий.

POST /api/v1/ingest/zabbix
POST /api/v1/ingest/solarwinds

Поведение — ровно как в AGENTS.md, правило 1:
1. Проверить аутентификацию вебхука.
2. Посчитать sha256 тела.
3. INSERT в raw_events (source, payload, payload_hash).
4. Ответить 202 с {"status": "accepted", "raw_event_id": N}.

Никакого парсинга payload на приёме. Тело принимается как произвольный JSON.
Неожиданное поле в payload не должно приводить к ошибке — это главное
требование к этому шагу.

Аутентификация: заголовок X-Webhook-Token (сравнение constant-time) плюс,
если задан секрет, HMAC-SHA256 тела в X-Webhook-Signature. Оба варианта
конфигурируются на источник.

Защита:
- Ограничение размера тела (по умолчанию 1 МБ) -> 413.
- Rate limit на источник (по умолчанию 200 запросов в секунду) -> 429.
- IP-allowlist, конфигурируемый, по умолчанию выключен.
- Конфликт по (source, payload_hash, received_at) -> 202 с тем же id,
  повторная доставка не считается ошибкой.

Тесты:
- Фикстуры реальных payload положить в backend/tests/fixtures/:
  zabbix_problem.json, zabbix_resolved.json, solarwinds_trigger.json.
  Взять их из раздела с примерами в «ФАЙЛИК ДЛЯ САШИ.md».
- Тест: payload с незнакомым полем всё равно принимается.
- Тест: неверный токен -> 401, неверная подпись -> 401.
- Тест: тело больше лимита -> 413.

Приёмка:
  POST фикстуры zabbix_problem.json -> 202, строка в raw_events, payload
  совпадает байт-в-байт с отправленным
```

## Шаг 3 — адаптеры источников

```
Реализуй нормализацию payload в канонический вид. Только детерминированный
код — никакого AI в этом слое.

Интерфейс в backend/app/adapters/sources/base.py:

    class SourceAdapter(Protocol):
        source: str
        def parse(self, payload: dict) -> CanonicalEvent: ...

CanonicalEvent — Pydantic-модель по формату из раздела 6 docs/tz.md.

ZabbixAdapter:
- external_key = event_id
- Время: поля timestamp/date/time приходят БЕЗ таймзоны, это локальное время
  сервера Zabbix. Смещение берётся из настройки ZABBIX_TZ и применяется явно.
  Захардкоженный UTC — ошибка, из-за неё все инциденты уедут на N часов.
- severity — по числовому event_nseverity через таблицу severity_map,
  не по строке.
- kind: PROBLEM -> problem, RESOLVED/OK -> resolved.
- host_ip == '*UNKNOWN*' -> None.
- Теги парсятся из event_tags.
- Всё, что не легло в поля канонической модели, уходит в attrs — item_key,
  item_name, opdata и прочее. Ничего не выбрасываем.

SolarWindsAdapter:
- external_key = f"{alert.objectId}|{alert.name}" — objectId это идентификатор
  УЗЛА, и без имени правила два разных алерта на одном узле затрут друг друга.
- Числового значения метрики отдельным полем нет, оно внутри текста
  alert.message. Регулярку-извлекатель написать, но при неудаче не падать:
  value остаётся None.
- Формат reset-события не подтверждён (открытый вопрос 1). Реализуй по
  гипотезе eventType in ('reset','resolved') -> kind=resolved и пометь место
  комментарием TODO с ссылкой на открытый вопрос.

Реестр адаптеров: словарь source -> адаптер, разрешение по строке. Добавление
третьего источника не должно требовать правок в существующих адаптерах.

Тесты: параметризованные, на всех фикстурах из шага 2. Проверять каждое поле
канонического события, включая корректность таймзоны и построение external_key.

Приёмка:
  все фикстуры парсятся, тесты зелёные
  добавление нового источника не меняет ни одного существующего файла,
  кроме реестра
```

## Шаг 4 — нормализатор

```
Реализуй воркер нормализации: raw_events -> monitored_objects, incidents,
incident_events.

backend/app/workers/normalizer.py — отдельный процесс, запускаемый как
самостоятельный сервис в compose.

Цикл:
1. Выбрать пачку:
     SELECT ... FROM raw_events WHERE processed_at IS NULL
     ORDER BY received_at LIMIT :batch FOR UPDATE SKIP LOCKED
2. По каждой записи:
   - адаптер -> CanonicalEvent
   - upsert monitored_objects по (source, external_id), обновить last_seen
   - fingerprint = sha256(source || object_external_id || rule_key)
   - upsert incidents через INSERT ... ON CONFLICT (source, external_key)
     DO UPDATE (правило 3 из AGENTS.md: порядок вебхуков не гарантирован)
   - INSERT в incident_events (только INSERT, никогда UPDATE)
   - processed_at = now()
3. Ошибка на записи: писать текст в process_error, processed_at НЕ ставить,
   продолжать пачку. Одно битое событие не должно останавливать поток.
4. Всё по одной записи — в одной транзакции.

Логика инцидента:
- kind=problem, инцидента нет      -> создать, status=open, dedup_count=1
- kind=problem, инцидент открыт    -> dedup_count += 1, last_event_at,
                                      severity и last_message обновить
- kind=problem, инцидент закрыт    -> открыть заново: status=open,
                                      resolved_at=NULL, opened_at=время события
- kind=resolved                    -> status=resolved, resolved_at
- событие старше last_event_at     -> в ленту записать, но состояние инцидента
                                      НЕ откатывать

Дедупликация: если last_notified_at внутри SUPPRESS_WINDOW (по умолчанию
15 минут), инцидент помечается как подавленный и уведомления не порождает.
Счётчик всё равно инкрементится.

Тесты:
- problem + resolved одного event_id -> ОДИН инцидент, два incident_events
- resolved пришёл раньше problem -> корректное итоговое состояние
- три одинаковых problem в окне -> один инцидент, dedup_count=3
- битый payload -> process_error заполнен, соседние записи обработаны
- перезапуск воркера в середине пачки -> ни одно событие не потеряно
  и не обработано дважды

Приёмка:
  прогон всех фикстур даёт ровно 2 инцидента и 3 incident_events
  (пример в конце db/schema.sql)
```

## Шаг 5 — пользователи, роли, LDAP, жизненный цикл учёток

```
Реализуй identity-слой. LDAP/AD — обязательная интеграция по условиям кейса,
поэтому это НЕ заглушка: пишем рабочую реализацию и проверяем против OpenLDAP
в контейнере.

Абстракция backend/app/adapters/identity/base.py:

    class IdentityProvider(Protocol):
        async def authenticate(self, username: str, password: str) -> Subject | None
        async def get_roles(self, subject_id: str) -> list[str]
        async def is_active(self, subject_id: str) -> bool

    @dataclass
    class Subject:
        subject_id: str      # objectGUID для LDAP, UUID для локального
        username: str
        roles: list[str]

LdapIdentityProvider (библиотека ldap3, основной провайдер):
- Bind сервисной учёткой, поиск пользователя по sAMAccountName, затем bind
  его учётными данными для проверки пароля. Пароль нигде не сохраняется
  и не кешируется.
- subject_id = objectGUID в строковом виде — стабилен при переименовании
  и переносе между OU.
- Роли: memberOf -> сопоставление с role_mappings по DN группы.
- LDAPS обязателен, проверка сертификата включена.
- Недоступность каталога -> роли из кеша user_roles, флаг деградации
  в /admin/dashboard/integrations.

LocalIdentityProvider — по таблице users, argon2id. НЕ удалять: нужен для
служебных учёток и аварийного входа администратора, иначе отказ AD запирает
вход в саму платформу.

ЖЁСТКО: ФИО, телефон и email в users не хранятся и в модель не добавляются.
Из каталога берём только objectGUID и членство в группах. См. раздел 5
AGENTS.md.

Тестовое окружение: контейнер OpenLDAP в docker-compose.dev.yml с
LDIF-фикстурой — 5 пользователей, 3 группы, соответствующие ролям admin,
engineer, viewer. Тесты идут против него, не против моков библиотеки.

Аутентификация:
- POST /api/v1/auth/login -> access (15 мин) и refresh (12 ч) в httpOnly
  Secure SameSite=Strict cookie. Токен в теле ответа не возвращать.
- POST /api/v1/auth/refresh с ротацией refresh-токена.
- POST /api/v1/auth/logout.
- GET /api/v1/auth/me -> subject_id, username, roles, отображаемое имя
  подтягивается из каталога на лету и в БД не пишется.
- Блокировка после 5 неудачных попыток на 15 минут (только для локального
  провайдера; для LDAP политика блокировок на стороне каталога).
- Каждый вход, выход и блокировка -> audit_log.

Жизненный цикл учётных записей (FR-IDM, требование критерия ИБ):
- Синхронизация ролей при входе и по расписанию LDAP_SYNC_INTERVAL
  (по умолчанию 1 час). Роли с source='local' синхронизация не затирает.
- Учётка отключена или отсутствует в каталоге -> is_active=false, активные
  сессии отзываются, новые уведомления пользователю не создаются.
  Подписки НЕ удаляются: при восстановлении учётки они возвращаются.
- Смена состава групп -> роли пересчитываются -> обязательные подписки старой
  роли автоматически перестают действовать. Строки в subscriptions при этом
  не трогаются вообще: эффективная подписка вычисляется (см. шаг 6).
- Каждое изменение состава ролей -> audit_log с old_value и new_value.
- POST /api/v1/admin/ldap/sync — внеочередная синхронизация.

RBAC: зависимость require_roles("admin"). Роли admin, engineer, viewer —
матрица доступа в разделе 2 docs/tz.md.

Тесты:
- вход пользователем из OpenLDAP -> роли соответствуют группам
- неверный пароль -> 401, пароль не попал ни в логи, ни в БД
- отключение учётки в каталоге -> следующая синхронизация деактивирует
  пользователя и отзывает сессии
- перевод пользователя из группы engineers в группу viewers -> обязательные
  подписки инженера перестали действовать без правок в subscriptions
- каталог недоступен -> вход локального админа работает, роли остальных
  берутся из кеша
- доступ viewer к админскому эндпоинту -> 403

Приёмка:
  логин учёткой из каталога -> cookie установлены, /auth/me отдаёт роли
  из групп LDAP
  переключение AUTH_PROVIDER=local не требует правок кода
  в логах приложения нет ни пароля, ни токена
```

## Шаг 6 — темы и подписки

```
Реализуй каталог тем и механизм подписок. Это самая нетривиальная часть
доменной логики — сверься с разделом 4 AGENTS.md.

Темы (CRUD только для admin):
  GET    /api/v1/topics          список, доступен всем аутентифицированным
  POST   /api/v1/topics          admin
  PATCH  /api/v1/topics/{id}     admin
  DELETE /api/v1/topics/{id}     admin, мягкое удаление через is_active

match_rule валидировать Pydantic-моделью:
  sources: list[str] | None
  severity_min: int | None (0..5)
  object_groups: list[str] | None
  tags_any: list[str] | None
  tags_all: list[str] | None
Пустой объект = тема ловит все события.

Функция match_topic(incident, topic) -> bool: условия соединяются логическим И,
внутри списка — ИЛИ. Покрыть таблицей тестов на все комбинации.

Подписки:
  GET    /api/v1/subscriptions          мои: обязательные и добровольные
                                        отдельными группами
  POST   /api/v1/subscriptions          подписаться самому (origin=self)
  DELETE /api/v1/subscriptions/{id}     отписаться — ТОЛЬКО origin=self
  PATCH  /api/v1/subscriptions/{id}     каналы, muted_until
  POST   /api/v1/admin/subscriptions    назначить пользователю (origin=assigned)

Правила, нарушать которые нельзя:
- Обязательные подписки НЕ материализуются строками. Они вычисляются из
  topic_roles + user_roles. Иначе пришлось бы пересчитывать подписки при
  каждом изменении роли.
- Приоритет происхождения: mandatory_role > assigned > self.
- Отписаться можно только от self. Попытка удалить assigned -> 403.
- Обязательная подписка бьёт глушение: muted_until на ней игнорируется.
- Глушение добровольной подписки ограничено сверху 24 часами.

Сервис get_effective_subscriptions(user_id) читает вьюху
v_effective_subscriptions — не переписывай её логику на Python, вьюха уже
делает слияние трёх источников.

Тесты:
- пользователь с ролью, привязанной к теме, видит её как обязательную
- снятие роли убирает обязательную подписку без правок в subscriptions
- удаление assigned-подписки пользователем -> 403
- self-подписка на ту же тему, что и обязательная -> одна запись, origin
  = mandatory_role
- глушение обязательной темы не отключает доставку

Приёмка:
  сценарий: создать тему, привязать к роли engineer, выдать роль пользователю
  -> тема появилась в обязательных, отписаться нельзя
```

## Шаг 7 — маршрутизация и доставка

```
Замкни сквозной путь: инцидент -> уведомление -> инбокс.

Роутер (backend/app/workers/router.py):
1. Взять инциденты, по которым уведомления ещё не создавались.
2. Подобрать активные темы по match_rule.
3. Для каждой темы получить эффективных подписчиков.
4. Создать notifications со status=pending — по одной строке на пару
   (пользователь, канал).
5. Если пользователь подписан на несколько подходящих тем — уведомление ОДНО
   на канал (ограничение notifications_uq), тема пишется первая совпавшая.
6. Подписка заглушена или сработало окно подавления -> строка создаётся со
   status=skipped. Решение должно быть видно, а не молча пропущено.
7. Проставить incidents.last_notified_at.

Каналы (backend/app/adapters/channels/base.py):

    class NotificationChannel(Protocol):
        name: str
        async def send(self, notification: Notification, address: str | None) -> None

- WebChannel: доставка = сама строка в notifications, инбокс читает вьюху
  v_user_inbox. Основной канал.
- TrueConfChannel: ОБЯЗАТЕЛЕН по условиям кейса, пишется полностью.
  Отправка сообщения пользователю через серверный API TrueConf Server
  (авторизация по OAuth-токену приложения, endpoint из ENV). Доступа
  к боевому серверу нет, поэтому в docker-compose.dev.yml поднимается
  мок-сервер на FastAPI, повторяющий контракт: те же пути, коды ответов,
  формат ошибок, искусственные задержки и отказы. Тесты идут против мока,
  переключение на боевой сервер = смена TRUECONF_BASE_URL и токена.
  Заглушка, которая пишет в лог и возвращает успех, требованию не отвечает.
- EmailChannel: SMTP, конфигурируемый, TLS обязателен.

Резолв адреса (backend/app/adapters/contacts/base.py):

    class ContactResolver(Protocol):
        async def resolve(self, user_id: int, channel: str) -> str | None

LdapContactResolver — основной: email из атрибута mail, идентификатор TrueConf
из настраиваемого атрибута каталога. LocalContactResolver — по user_contacts,
для стенда без каталога.
Адрес получателя НИКОГДА не пишется в notifications и не попадает в логи —
резолвится в момент отправки и живёт только в памяти обработчика.

Воркер доставки (backend/app/workers/delivery.py):
- Разбор очереди через FOR UPDATE SKIP LOCKED (запрос в конце db/schema.sql).
- Ретраи с экспоненциальной задержкой: 1 мин, 5 мин, 30 мин; после третьей
  попытки -> status=failed.
- Несколько экземпляров воркера должны работать параллельно без дублей.

API инбокса:
  GET   /api/v1/notifications                 мои, пагинация, фильтр unread
  GET   /api/v1/notifications/unread-count
  POST  /api/v1/notifications/{id}/read
  POST  /api/v1/notifications/read-all
  GET   /api/v1/notifications/{id}/delivery   история доставки: канал, статус,
                                              попытки, ошибка, время

Тесты:
- инцидент по теме с двумя подписчиками -> два уведомления
- подписка на две подходящие темы -> одно уведомление на канал
- заглушенная подписка -> status=skipped, не pending
- деактивированный пользователь -> уведомления не создаются
- падение SMTP -> attempts растёт, next_retry_at выставлен, после третьей
  попытки failed
- мок TrueConf отвечает 500 -> ретрай, затем failed с текстом ошибки
- мок TrueConf отвечает 200 -> status=sent, адрес получателя отсутствует
  и в БД, и в логах
- два экземпляра delivery-воркера на одной очереди -> ни одного дубля

Приёмка (СКВОЗНОЙ ПУТЬ — главная проверка проекта):
  POST фикстуры на /api/v1/ingest/zabbix
  -> raw_events -> incidents -> notifications -> GET /notifications
  показывает уведомление. Время от вебхука до инбокса меньше 5 секунд.
```

## Шаг 9 — реестр источников и универсальный API

```
Сделай подключение новой системы мониторинга операцией администратора,
а не задачей разработчика. Это требование кейса: масштабирование без
изменения ядра.

Таблица event_sources уже есть в db/schema.sql — реализуй работу с ней.

Три уровня подключения (FR-SRC в docs/tz.md):

1. kind='canonical'. POST /api/v1/ingest/generic — тело уже в каноническом
   формате из раздела 7 docs/tz.md. Адаптер не нужен вообще.

2. kind='mapping'. POST /api/v1/ingest/{source_code} — преобразование задаётся
   выражениями JSONPath в event_sources.field_map:
     {
       "external_key":       "$.alerts[0].fingerprint",
       "severity_raw":       "$.alerts[0].labels.severity",
       "object.external_id": "$.alerts[0].labels.instance",
       "object.name":        "$.alerts[0].labels.instance",
       "message":            "$.alerts[0].annotations.summary",
       "occurred_at":        "$.alerts[0].startsAt",
       "kind_map":           {"firing": "problem", "resolved": "resolved"}
     }
   MappingAdapter применяет field_map и отдаёт CanonicalEvent. Ошибка
   выражения -> process_error, событие не теряется.

3. kind='adapter'. Как сейчас у Zabbix и SolarWinds: класс SourceAdapter,
   зарегистрированный по имени в event_sources.adapter_class.

Аутентификация по источнику: token_hash и hmac_secret хранятся в
event_sources, у каждого источника свои. Ротация токена одного источника
не влияет на остальные. Неактивный источник -> 403.

Админские эндпоинты:
  GET  POST   /api/v1/admin/sources           список, регистрация
  PUT DELETE  /api/v1/admin/sources/{code}    изменение, отключение
  POST        /api/v1/admin/sources/{code}/rotate-token
  POST        /api/v1/admin/sources/{code}/test
       тело: пример payload -> ответ: получившийся CanonicalEvent или
       понятная ошибка разбора. Ключевая вещь для интегратора: маппинг
       настраивается за минуты, а не подбором вслепую.

Все изменения источников -> audit_log.

Тесты:
- канонический payload на /ingest/generic -> инцидент создан
- payload Prometheus Alertmanager через field_map -> инцидент создан
  БЕЗ единой строки нового кода
- битое выражение JSONPath -> process_error, соседние события обработаны
- токен источника A не подходит источнику B -> 401
- отключение источника -> 403, остальные работают

Приёмка:
  подключение Prometheus Alertmanager делается через админку целиком:
  создать источник, вставить пример payload, настроить маппинг, проверить
  кнопкой «тест», выдать токен. Это ровно тот сценарий, который надо
  показать на защите.
```

```
10. Экономика: пересчёт эффекта на цифрах прогона по docs/economics.md.

scripts/demo_seed.py — приведение стенда в демонстрационное состояние:
пользователи с разными ролями, темы, подписки, набор инцидентов разной

scripts/demo_reset.py — откат к чистому состоянию.

README.md в корне: что это, как поднять с нуля тремя командами, как прогнать
```

## Что осталось неопределённым

Эти вопросы в промптах помечены, но ответа на них пока нет. Их надо закрыть
опытным путём на стендах — до того, как они всплывут на защите.

| # | Вопрос | Где влияет | Чем грозит |
|---|---|---|---|
| 1 | Формат `reset`-события SolarWinds | шаг 3 | **Блокирующий.** Инциденты SolarWinds не будут закрываться |
| 2 | Таймзона сервера Zabbix | шаг 3 | Все инциденты смещены на N часов |
| 3 | Реальная шкала severity SolarWinds | шаг 1, сид | Неверный приоритет, неверная маршрутизация |
| 4 | Формат ack-события | шаг 4 | Отложено, но поля в схеме уже есть |
| 5 | Сетевая достижимость ВМ №3 от источников | шаг 2 | Вебхуки не дойдут — проверить до сборки |
| 6 | Ресурсы ВМ №4 и какая модель влезет | шаг 8 | Определяет размер модели и таймауты |
| 7 | Пересечение хостов между Zabbix и SolarWinds | вне MVP | Определяет, нужен ли слой связывания объектов |
| 8 | Доступ к TrueConf Server и токен приложения | шаг 7 | Канал обязателен по кейсу. Без доступа демонстрируем на мок-сервере — реализация от этого не меняется |
| 9 | Доступ к боевому AD | шаг 5 | Интеграция обязательна по кейсу. Проверяем против OpenLDAP с воспроизведённой структурой групп |

Вопросы 1 и 5 стоит проверить в первый же день: первый ломает логику закрытия
инцидентов, второй — вообще весь путь. Вопросы 8 и 9 — запросить у
организаторов сразу, ответ может прийти не мгновенно, а работа по ним идёт
параллельно на подстановках.
