# Техническое задание: платформа интеллектуального управления оповещениями

Версия 1.1 · 2026-08-10 · IT CAMP 2026, кейс Газпром нефти

---

## 1. Назначение

Система принимает события от разнородных систем мониторинга, приводит их к
единому формату, устраняет дубликаты, определяет заинтересованных получателей и
доставляет уведомления по подпискам. Дополнительно формирует человекочитаемую
сводку инцидента средствами локальной языковой модели.

Система **не заменяет** Zabbix и SolarWinds — она надстраивается над ними.
Пороги, триггеры и сбор метрик остаются в источниках.

### 1.1. Бизнес-показатели заказчика

Исходные данные и цели из кейса — по ним нас будут оценивать:

| Показатель | Как есть | Цель |
|---|---|---|
| События в сутки | 5400 от 7 систем | обрабатываются полностью |
| Шум (закрыто без реакции за 2 мин) | 65 % | сокращение за счёт дедупликации и подписок |
| Ручная фильтрация у дежурной смены NOC | 48 чел-часов/сутки | −60 % |
| MTTR | не измеряется системно | ≤ 20 минут |
| Ложные срабатывания | — | ≤ 5 % |
| Время незамеченного простоя | 14 минут | секунды до попадания в инбокс |

Пилотный периметр: Блок разведки и добычи, 4 филиала, 87 пользователей,
источники Zabbix (АСУ ТП) и SolarWinds (сетевое оборудование).

### 1.2. Технические показатели прототипа

| Показатель | Значение |
|---|---|
| Пропускная способность приёма | 100 событий/сек без потерь (пик), 10–50/мин штатно |
| Задержка «вебхук → инцидент в БД» | ≤ 2 с при штатной нагрузке |
| Задержка «инцидент → уведомление в инбоксе» | ≤ 5 с |
| Доля схлопнутых дубликатов на шторме | ≥ 80 % при повторах в окне подавления |
| Потеря событий при перезапуске воркера | 0 (событие уже в `raw_events`) |

Заявленные 5400 событий в сутки — это в среднем 0,06 события в секунду.
Наш запас по приёму — более чем стократный, и он взят не «на всякий случай»,
а под шторм: при аварии магистрали сотни событий приходят за секунды.
При этом решение не создаёт избыточной инфраструктурной нагрузки — брокера
сообщений и кеша в контуре нет, очередь живёт в той же БД.

## 2. Роли пользователей

| Роль | Код | Возможности |
|---|---|---|
| Администратор платформы | `admin` | Управление темами, назначение подписок, управление пользователями и маппингом ролей, просмотр аудита |
| Инженер / дежурный | `engineer` | Просмотр инцидентов и инбокса, самостоятельная подписка на доступные темы, глушение необязательных подписок |
| Наблюдатель | `viewer` | Просмотр дашборда инцидентов без права подписки |

Роли приходят из каталога (AD-группы → внутренние роли через `role_mappings`).
Назначать `assigned`-подписки может только `admin` — промежуточной роли
руководителя в прототипе нет.

Соответствие выгодоприобретателям из кейса: дежурная смена NOC и инженеры
эксплуатации — `engineer`; бизнес-заказчики сервисов, получающие уведомления
о деградации своего контура, — `viewer` с добровольными подписками на темы
своих сервисов; владелец платформы — `admin`.

Три роли — это минимум, покрывающий пилот. Модель ролей расширяемая: роль
заводится записью в `roles` и маппингом на группу каталога, код при этом
не меняется.

## 3. Функциональные требования

### 3.1. Приём событий (FR-IN)

- **FR-IN-1.** Система принимает HTTP POST на `/api/v1/ingest/{source}`, где
  `source ∈ {zabbix, solarwinds}`.
- **FR-IN-2.** Обработчик выполняет ровно одну операцию — вставку тела запроса
  в `raw_events` — и возвращает `202 Accepted`. Парсинг на приёме запрещён:
  неожиданное поле не должно приводить к потере события.
- **FR-IN-3.** Приём принимает как `application/json`, так и
  `application/x-www-form-urlencoded` (SolarWinds шлёт query-параметры).
- **FR-IN-4.** Повторная доставка одного и того же тела в пределах партиции
  отбрасывается по `sha256(payload)`.
- **FR-IN-5.** Запрос без валидного токена источника или с неверной
  HMAC-подписью отклоняется с `401`, факт пишется в журнал безопасности.
- **FR-IN-6.** Тело больше 256 КБ отклоняется с `413`.
- **FR-IN-7.** Универсальный эндпоинт `/api/v1/ingest/generic` принимает событие
  уже в каноническом формате (раздел 7). Система, умеющая слать такой JSON,
  подключается **без написания адаптера** — только регистрацией источника.
- **FR-IN-8.** Источник — запись в реестре `event_sources`: код, название,
  токен, HMAC-секрет, IP-allowlist, признак активности, ссылка на адаптер или
  декларативный маппинг. Отключение источника не влияет на остальные.

### 3.1.1. Подключение нового источника (FR-SRC)

Требование кейса: подключение новых источников без изменения ядра. Три уровня
сложности, от самого дешёвого:

- **FR-SRC-1. Каноническая отправка.** Источник шлёт готовый канонический JSON
  на `/ingest/generic`. Работы: создать источник в админке, выдать токен.
  Ноль строк кода.
- **FR-SRC-2. Декларативный маппинг.** Источник шлёт свой JSON, соответствие
  полей описывается выражениями JSONPath в конфигурации источника
  (`field_map`), включая таблицу перевода severity. Работы: заполнить форму
  в админке. Ноль строк кода.
- **FR-SRC-3. Адаптер кодом.** Нужен, когда преобразование не выражается
  маппингом — как разбор `alert.message` у SolarWinds. Работы: новый класс,
  реализующий `SourceAdapter`, и запись в реестре. Существующие адаптеры и ядро
  не затрагиваются.

Prometheus Alertmanager, Tibbo AggreGate и Saymon из кейса покрываются
уровнями 1–2 и в прототипе демонстрируются подключением без правки кода.

### 3.2. Нормализация (FR-NORM)

- **FR-NORM-1.** Фоновый обработчик выбирает необработанные записи запросом с
  `FOR UPDATE SKIP LOCKED` и применяет адаптер соответствующего источника.
- **FR-NORM-2.** Адаптер приводит событие к каноническому виду:
  `source_system`, `source_event_id`, `severity`, `object`, `message`,
  `occurred_at`, `tags`.
- **FR-NORM-3.** Severity приводится к общей шкале 0–5 по таблице
  `severity_map`; исходное значение сохраняется в `severity_raw`.
- **FR-NORM-4.** Наблюдаемый объект дедуплицируется по
  `(source, external_id)`; при повторной встрече обновляется `last_seen`.
- **FR-NORM-5.** Ошибка нормализации записывается в `process_error`, событие
  остаётся в `raw_events` и доступно для повторной обработки после исправления
  маппинга. Ошибка одного события не останавливает конвейер.
- **FR-NORM-6.** Нормализация выполняется детерминированным кодом. Применение
  языковой модели на этом слое исключено.

**Таймзона.** Zabbix отдаёт `timestamp`/`date`/`time` без таймзоны — это
локальное время сервера Zabbix. Смещение задаётся конфигурацией
`ZABBIX_TZ` для каждого источника. При отсутствии настройки используется время
приёма вебхука. Ошибка здесь смещает все инциденты на N часов.

### 3.3. Инциденты и дедупликация (FR-INC)

- **FR-INC-1.** Инцидент идентифицируется парой `(source, external_key)`:
  - Zabbix: `event_id`
  - SolarWinds: `alert.objectId ‖ '|' ‖ alert.name` — `objectId` это
    идентификатор узла, и два разных правила на одном узле иначе затрут друг друга
- **FR-INC-2.** Запись выполняется через `INSERT ... ON CONFLICT DO UPDATE` —
  порядок доставки PROBLEM и RESOLVED не влияет на результат.
- **FR-INC-3.** `fingerprint = sha256(source ‖ object_external_id ‖ rule_key)`
  вычисляется при нормализации и хранится в инциденте.
- **FR-INC-4.** Если приходит событие с fingerprint уже открытого инцидента,
  и с момента последнего уведомления прошло меньше окна подавления
  (`SUPPRESS_WINDOW`, по умолчанию 15 минут) — инкрементится `dedup_count`,
  обновляется `last_event_at`, новое уведомление **не создаётся**.
- **FR-INC-5.** Событие восстановления переводит инцидент в `resolved`,
  проставляет `resolved_at`; `duration_s` вычисляется автоматически.
- **FR-INC-6.** Каждое событие добавляет запись в ленту `incident_events`.
- **FR-INC-7.** Инциденты с признаком `is_test` не попадают в основной дашборд
  и не порождают уведомлений.

### 3.4. Темы и подписки (FR-SUB)

- **FR-SUB-1.** Администратор ведёт каталог тем. Тема содержит код, название,
  описание и правило отбора `match_rule` (JSON: источник, диапазон severity,
  группы объектов, теги).
- **FR-SUB-2.** Тема может быть привязана к одной или нескольким ролям — для
  носителей роли подписка обязательна и отписаться от неё нельзя.
- **FR-SUB-3.** Администратор может назначить тему конкретному пользователю
  (`assigned`). Такая подписка также не снимается пользователем.
- **FR-SUB-4.** Пользователь может самостоятельно подписаться на любую активную
  тему, не назначенную ему принудительно (`self`), и отписаться от неё.
- **FR-SUB-5.** Эффективный набор подписок — объединение трёх источников.
  При совпадении темы приоритет происхождения:
  `mandatory_role > assigned > self`.
- **FR-SUB-6.** Пользователь может временно заглушить подписку (`muted_until`).
  Для обязательных подписок длительность глушения ограничена
  `MAX_MUTE_MINUTES` (по умолчанию 60 минут).
- **FR-SUB-7.** Экран подписок — один, с двумя вкладками: «Обязательные» и
  «Доступные». Фильтров по severity, тегам и объектам в интерфейсе нет.
- **FR-SUB-8.** Любое изменение темы, привязки к роли или назначенной подписки
  фиксируется в `audit_log`.

### 3.5. Маршрутизация и доставка (FR-DLV)

- **FR-DLV-1.** При появлении нового инцидента (или его эскалации по severity)
  обработчик подбирает темы, чьё `match_rule` удовлетворено, разворачивает их в
  эффективных подписчиков и создаёт записи `notifications` в статусе `pending`.
- **FR-DLV-2.** Один пользователь получает по инциденту одно уведомление на
  канал, даже если инцидент подошёл под несколько его тем.
- **FR-DLV-3.** Каналы доставки: `web` (инбокс внутри приложения), `trueconf`
  (корпоративный мессенджер, обязателен по условиям кейса) и `email` (SMTP).
  Набор каналов расширяется новым классом `NotificationChannel` без правки
  маршрутизатора.
- **FR-DLV-4.** Адрес доставки резолвится в момент отправки через
  `ContactResolver` и не сохраняется ни в БД, ни в логах.
- **FR-DLV-5.** Неуспешная доставка повторяется с экспоненциальной задержкой,
  максимум `MAX_DELIVERY_ATTEMPTS` (по умолчанию 5), затем статус `failed` с
  текстом ошибки.
- **FR-DLV-6.** Веб-инбокс показывает уведомления с отметкой о прочтении и
  ссылкой на карточку инцидента.
- **FR-DLV-7.** Доставка в TrueConf идёт через серверный API корпоративного
  сервера мессенджера. Адресация — по идентификатору пользователя TrueConf,
  полученному из каталога в момент отправки; в базе он не хранится.
- **FR-DLV-8.** История доставки по каждому уведомлению доступна в интерфейсе:
  канал, статус, число попыток, текст ошибки, время.

### 3.5.1. Управление жизненным циклом учётных записей (FR-IDM)

Прямое требование критерия информационной безопасности.

- **FR-IDM-1.** Аутентификация через LDAP/AD. Пароль пользователя каталога
  система не хранит и не кеширует.
- **FR-IDM-2.** Роли определяются членством в группах каталога через
  `role_mappings`. Локальное назначение ролей возможно, но помечается
  `source='local'` и синхронизацией не затирается.
- **FR-IDM-3.** Синхронизация ролей — при каждом входе и по расписанию
  (`LDAP_SYNC_INTERVAL`, по умолчанию 1 час).
- **FR-IDM-4. Увольнение.** Учётка отключена или удалена в каталоге →
  `is_active = false`, сессии отзываются, уведомления пользователю больше не
  создаются. Подписки не удаляются: при восстановлении учётки они возвращаются.
- **FR-IDM-5. Смена должности.** Изменился состав групп → пересчитываются роли
  → обязательные подписки прежней роли перестают действовать, новой —
  начинают. Материализованных строк править не нужно, эффективная подписка
  вычисляется (см. FR-SUB-5).
- **FR-IDM-6.** Каждое изменение состава ролей пишется в `audit_log` с прежним
  и новым значением.
- **FR-IDM-7.** Недоступность каталога не роняет систему: роли берутся из кеша
  `user_roles`, факт деградации отражается в админском дашборде.

### 3.5.2. Административный дашборд платформы (FR-ADM)

Отдельный пункт задания. Показывает состояние **платформы**, а не инцидентов.

- **FR-ADM-1.** Нагрузка: события в минуту по источникам, глубина очереди
  нормализации, глубина очереди доставки.
- **FR-ADM-2.** Обработано событий: принято, нормализовано, ошибок
  нормализации — за выбранный период.
- **FR-ADM-3.** Эффективность фильтрации: сколько событий пришло, сколько
  инцидентов создано, коэффициент дедупликации, доля подавленных повторов.
  Это главная цифра защиты — она показывает снижение шума в разах.
- **FR-ADM-4.** Доставка: процент доставленных уведомлений, разбивка по
  каналам, число `failed` с причинами.
- **FR-ADM-5.** Топ инцидентов: самые частые правила и самые проблемные
  объекты за период.
- **FR-ADM-6.** Задержки конвейера: p50/p95/p99 на участках «приём →
  нормализация» и «инцидент → уведомление».
- **FR-ADM-7.** Состояние интеграций: последнее событие от каждого источника,
  доступность каталога, доступность модели, доступность SMTP и TrueConf.
- **FR-ADM-8.** Данные дашборда считаются агрегирующими запросами по
  `raw_events`, `incidents` и `notifications`. Отдельной системы метрик
  в контуре не появляется.

### 3.6. Языковая модель (FR-AI)

- **FR-AI-1.** Для нового инцидента формируется сводка: что произошло, на каком
  объекте, насколько критично, на что обратить внимание.
- **FR-AI-2.** Обращение к модели идёт через OpenAI-совместимый endpoint,
  адрес и имя модели задаются переменными окружения.
- **FR-AI-3.** Отправляется по одному инциденту за запрос. Пакетная обработка и
  корреляция нескольких инцидентов в прототип не входят.
- **FR-AI-4.** Недоступность модели не блокирует доставку: уведомление уходит
  без сводки, попытка повторяется отдельным обработчиком.
- **FR-AI-5.** Сводка сохраняется с указанием модели и версии промпта, чтобы
  результаты были воспроизводимы и сравнимы.
- **FR-AI-6.** Маскирование имён хостов и адресов перед отправкой реализовано
  как переключаемая функция, по умолчанию выключенная — модель работает внутри
  контура.
- **FR-AI-7.** Модуль вынесен на отдельные вычислительные ресурсы (ВМ №4) и
  общается с ядром по HTTP. Его недоступность или перегрузка не влияют на
  сквозной путь доставки.

### 3.7. Границы применения ИИ и обоснование

**Где ИИ применяется:** саммаризация инцидента.

**Где не применяется и почему:** нормализация, дедупликация и определение
критичности выполняются детерминированным кодом. Три причины, которые нужно
уметь назвать на защите:

1. **Объяснимость.** Если уведомление ушло не тому дежурному, разбор должен
   упираться в конкретную строку правила. «Модель так решила» — не ответ для
   службы эксплуатации промышленного объекта.
2. **Задержка и отказоустойчивость.** Путь «событие → инбокс» обязан
   укладываться в 5 секунд. Модель на этом участке добавляет и задержку,
   и точку отказа.
3. **Воспроизводимость.** Требование по ложным срабатываниям (≤ 5 %) проверяется
   повторным прогоном одних и тех же событий. Детерминированный код это
   гарантирует, генеративная модель — нет.

При этом порог для ИИ снижается, а не закрывается: как только исторический
корпус событий накоплен, сценарии ниже подключаются как надстройка над тем же
конвейером, не переписывая его.

### 3.8. Сценарии применения ИИ: реализация и дорожная карта

| # | Сценарий | Бизнес-ценность | Статус |
|---|---|---|---|
| 1 | **Саммаризация инцидента.** Технический алерт → 2–4 предложения: что случилось, чем грозит, что проверить первым | Дежурному L1 не нужно расшифровывать `vfs.fs.size[/,pfree]<10`. Сокращает время принятия решения и снижает требования к квалификации первой линии | **Реализовано** |
| 2 | **Семантическая нормализация.** Приведение разноформатных сообщений к единому смыслу, когда поля не совпадают структурно | Подключение источника без ручного маппинга. Даёт эффект начиная с 4–5 систем, в пилоте с двумя — избыточно | Концепция |
| 3 | **Определение дубликатов по смыслу.** Вторая линия поверх fingerprint: «сервер не отвечает» из Zabbix и «узел недоступен» из SolarWinds — один инцидент | Устранение двойных оповещений от связанных систем — прямо названо узким местом в кейсе | Концепция |
| 4 | **Корреляция в цепочки и определение первопричины.** Падение коммутатора порождает 40 алертов от зависимых узлов; система показывает один корневой | Снижение шума кратно, а не на проценты. Наибольший потенциальный эффект из всех сценариев | Концепция |
| 5 | **Интеллектуальная маршрутизация по истории.** Кто фактически закрывал похожие инциденты — тому и адресовать | Устраняет ручной поиск ответственного обзвоном (сценарий P0 из кейса) | Концепция |
| 6 | **Рекомендации из базы знаний.** Подсказка по устранению на основе прошлых разборов | Прямое влияние на MTTR: инженер не ищет решение с нуля | Концепция |

Сценарии 3–5 требуют исторического корпуса — в кейсе он заявлен объёмом 2 ТБ
логов и двумя серверами с GPU NVIDIA A30. На стенде хакатона такого корпуса
нет, поэтому они и остаются проработанной концепцией: обучать нечем и не на чем.
Это ограничение данных, а не архитектуры — точки подключения в конвейере
предусмотрены (после нормализации и перед маршрутизацией).

### 3.9. Заложено, но не реализуется в прототипе (FR-FUT)

- **FR-FUT-1. Квитирование.** Дежурный отмечает, что взял инцидент в работу;
  повторные напоминания прекращаются, видно ответственного. Поля
  `acknowledged`, `ack_by`, `ack_at` в схеме присутствуют, эндпоинт возвращает
  `501 Not Implemented` при выключенном флаге функции.
- **FR-FUT-2. Эскалация.** Если инцидент не квитирован за N минут, уведомление
  уходит следующему получателю. Требует таблицы уровней эскалации.
- **FR-FUT-3. Интеграция с ServiceDesk.** Автоматическое создание заявки с
  дедлайном (сценарий P2 из кейса). Контракт совпадает с `NotificationChannel`.
- **FR-FUT-4. Обогащение из CMDB.** Владелец сервиса, критичность бизнес-
  процесса, зона ответственности по геотегу. В прототипе роль упрощённой CMDB
  играет `monitored_objects` с группами объектов.

## 4. Нефункциональные требования

### 4.1. Безопасность

| Категория | Требование |
|---|---|
| Транспорт | TLS на nginx, HSTS, редирект с HTTP. Порт БД не публикуется |
| Заголовки | CSP без `unsafe-inline`/`unsafe-eval`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options: DENY` |
| Пароли | argon2id, минимум 12 символов, блокировка после 5 неудач на 15 минут |
| Сессии | JWT в `httpOnly Secure SameSite=Strict` cookie, access 15 мин, refresh 12 ч с ротацией |
| Вебхуки | Токен источника + HMAC-SHA256 подпись тела, IP-allowlist, rate limit |
| Ввод | Pydantic с `extra="forbid"` на всех схемах запросов |
| SQL | Только ORM с параметризацией; конкатенация строк в запросах запрещена |
| Контейнеры | non-root, read-only rootfs, `no-new-privileges`, drop capabilities, лимиты ресурсов |
| Секреты | Через переменные окружения из файла с правами `600`; в репозиторий не попадают |
| Аудит | Изменения тем, ролей, подписок; входы и неудачные попытки входа |
| Зависимости | Фиксация версий с хешами, `pip-audit` и `trivy` в CI, SBOM в формате CycloneDX |

### 4.2. Персональные данные

Изложено в разделе 5 `AGENTS.md` и обязательно к соблюдению. Кратко:
хранится непрозрачный `subject_id` и роли; ФИО, телефон и email не хранятся;
email резолвится на лету; логи не содержат адресов и тел уведомлений.
Единственное исключение на время MVP — таблица `user_contacts`, помеченная как
содержащая ПДн и очищаемая при переходе на каталог.

### 4.3. Наблюдаемость самой системы

- `/healthz` — живость процесса, `/readyz` — доступность БД и миграций
- Структурные логи в JSON, обязательное поле `request_id`
- Счётчики: принято событий, глубина очереди, ошибки нормализации, отправлено и
  провалено уведомлений, задержка обработки
- Логи не содержат payload событий, адресов доставки и тел уведомлений

### 4.4. Хранение и ретеншен

| Данные | Срок | Механизм |
|---|---|---|
| `raw_events` | 30 дней | Помесячные партиции, дроп старых |
| `incident_events` | 12 месяцев | Помесячные партиции |
| `incidents` | бессрочно | — |
| `notifications` | 90 дней | Удаление по расписанию |
| `audit_log` | 12 месяцев | — |

Резервное копирование: суточный `pg_basebackup` плюс непрерывная архивация WAL,
хранение копий 30 суток, ежемесячная проверка восстановлением на тестовом
контуре. Цели восстановления для пилота: RPO ≤ 5 минут, RTO ≤ 30 минут.

### 4.5. Отказоустойчивость

| Отказ | Поведение системы |
|---|---|
| Падение воркера нормализации | События остаются в `raw_events` с `processed_at IS NULL`, после подъёма разбираются. Потерь нет |
| Падение воркера доставки | Уведомления остаются `pending`, `SKIP LOCKED` не даёт двойной отправки при параллельных воркерах |
| Недоступность SMTP или TrueConf | Ретраи с экспоненциальной задержкой, затем `failed` с причиной; веб-инбокс продолжает работать |
| Недоступность языковой модели | Уведомление уходит без сводки, сводка подтягивается позже |
| Недоступность каталога | Роли берутся из кеша `user_roles`, вход локальных админов сохраняется |
| Падение БД | Единая точка отказа. Смягчение: потоковая репликация на второй узел с ручным переключением |
| Перезагрузка ВМ источника | Вебхуки не приходят; факт виден в дашборде как «нет событий от источника N минут» |

Приём событий отделён от обработки намеренно: это делает потерю событий
невозможной при любом отказе за пределами самой БД.

### 4.6. Импортозамещение

Условие кейса: использовать отечественные продукты либо предусмотреть
возможность их использования. Таблица замещения — раздел 2 `AGENTS.md`.
Ключевое: PostgreSQL → Postgres Pro, ОС → Astra Linux SE или РЕД ОС, Docker →
Podman, языковая модель — российская или открытая в self-hosted-варианте.
Ни один компонент не требует переписывания кода при замене.

## 5. Архитектура

### 5.1. Компоненты

| Компонент | Ответственность | Развёртывание |
|---|---|---|
| `nginx` | TLS, раздача статики фронта, проксирование `/api` | Контейнер, ВМ №3 |
| `frontend` | Nuxt 3 `ssr:false`, собирается в статику на этапе сборки | Артефакт сборки |
| `api` | FastAPI: приём вебхуков, REST для UI, аутентификация | Контейнер, ВМ №3 |
| `worker` | Нормализация, маршрутизация, доставка, сводки LLM | Контейнер, ВМ №3 |
| `db` | PostgreSQL 16: данные и очередь | Контейнер, ВМ №3 |
| `llm` | Локальная модель, OpenAI-совместимый API | ВМ №4, вне Docker |

`api` и `worker` — один образ с разными точками входа. Общий код, разные
процессы: приём не должен тормозить из-за обработки.

### 5.2. Конвейер обработки

```
① Приём          POST /api/v1/ingest/{source}
                 INSERT INTO raw_events → 202
                 никакого парсинга

② Нормализация   SELECT ... WHERE processed_at IS NULL
                 FOR UPDATE SKIP LOCKED LIMIT 100
                 адаптер источника → канонический вид
                 upsert monitored_objects
                 fingerprint → upsert incidents
                 INSERT incident_events
                 UPDATE processed_at

③ Маршрутизация  новый / эскалированный инцидент
                 подобрать темы по match_rule
                 развернуть в эффективных подписчиков
                 проверить окно подавления и mute
                 INSERT notifications (pending)

④ Доставка       SELECT pending FOR UPDATE SKIP LOCKED
                 web   → уведомление становится видимым в инбоксе
                 email → ContactResolver → SMTP
                 retry с экспоненциальной задержкой

⑤ Сводка LLM     инцидент без сводки → локальная модель
                 INSERT llm_summaries
                 недоступность модели не блокирует ④
```

Каждая стрелка — отдельный тестируемый кусок. Сначала прогоняем одно событие
через все пять шагов, потом наращиваем функциональность.

### 5.3. Абстракции, обязательные к соблюдению

| Интерфейс | Реализация в MVP | Будущая реализация |
|---|---|---|
| `SourceAdapter` | `ZabbixAdapter`, `SolarWindsAdapter`, `GenericAdapter` (канонический формат), `MappingAdapter` (декларативный маппинг) | Любой третий источник — новый класс, существующие не трогаются |
| `IdentityProvider` | `LdapIdentityProvider` (основной), `LocalIdentityProvider` (аварийный вход админа) | Выбор через `AUTH_PROVIDER` |
| `ContactResolver` | `LdapContactResolver` — адрес по запросу, без хранения; `LocalContactResolver` для стенда | — |
| `NotificationChannel` | `WebChannel`, `TrueConfChannel`, `EmailChannel` | SMS, push — новый класс |
| `LlmClient` | `OpenAiCompatibleClient` | смена endpoint через env, код не меняется |

**Локальный провайдер не исчезает.** Он остаётся для служебных учёток и
аварийного входа администратора при недоступности каталога — иначе отказ AD
запирает вход в саму платформу.

## 7. Канонический формат события

Промежуточный вид, к которому адаптер приводит любой источник до записи в
инцидент.

```json
{
  "source_system": "zabbix",
  "source_event_id": "8841203",
  "external_key": "8841203",
  "kind": "problem",
  "severity": 4,
  "severity_raw": "High",
  "object": {
    "external_id": "db-prod-03",
    "name": "db-prod-03",
    "ip": "10.0.3.14",
    "type": "server"
  },
  "rule": {
    "key": "25239",
    "name": "Диск заполнен на 94%",
    "expression": "last(/db-prod-03/vfs.fs.size)>90"
  },
  "message": "Диск заполнен на 94%",
  "value": "94",
  "occurred_at": "2026-07-10T02:14:00Z",
  "tags": ["disk", "prod", "msk-dc1"],
  "is_test": false,
  "attrs": {}
}
```

| Поле | Зачем |
|---|---|
| `source_system` | Не терять контекст происхождения |
| `severity` | Приводится к общей шкале уже на входе |
| `object` | Без него не построить ни группировку, ни маршрутизацию |
| `tags` | Свободные метки для правил отбора тем |
| `external_key` | Ключ склейки событий одного инцидента |

### 7.1. Соответствие полей источников

| Каноническое | Zabbix | SolarWinds |
|---|---|---|
| `source_event_id` | `event_id` | `alert.objectId` |
| `external_key` | `event_id` | `alert.objectId ‖ '|' ‖ alert.name` |
| `kind` | `status`: PROBLEM/RESOLVED | `eventType`: trigger/reset |
| `severity_raw` | `severity` | `alert.severity` |
| severity источник истины | `event_nseverity` (число надёжнее строки) | `alert.severity` |
| `object.external_id` | `host_technical_name` | `node.objectId` |
| `object.name` | `host` | `node.name` |
| `object.ip` | `host_ip` (`*UNKNOWN*` → null) | `node.ipAddress` |
| `rule.key` | `trigger_id` | `alert.name` |
| `rule.name` | `trigger_name` | `alert.name` |
| `rule.expression` | `trigger_expression` | `alert.description` |
| `value` | `item_lastvalue` | нет отдельного поля — остаётся `null` |
| `occurred_at` | `timestamp` + `ZABBIX_TZ` | время из payload |
| `is_test` | по группе `Test webhook group` | `meta.testEvent` |

**Значение метрики у SolarWinds.** Число (например, «94%») спрятано внутри
текста `alert.message`, отдельного поля нет. Решение: оставляем `value = null`,
регулярными выражениями текст не разбираем.

## 8. Открытые вопросы

| № | Вопрос | Влияние | Как закрыть |
|---|---|---|---|
| 1 | Формат `reset`-события SolarWinds не подтверждён. Если в нём нет того же `objectId` — `external_key` придётся строить иначе | **Блокирующий** для склейки инцидентов SolarWinds | Дождаться реального срабатывания либо вызвать действие через Action Manager |
| 2 | Шкала severity SolarWinds выписана по памяти | Неверный приоритет инцидентов | Сверить с реальной шкалой Orion |
| 3 | Таймзона сервера Zabbix | Все инциденты смещены на N часов | Задать `ZABBIX_TZ` явно, проверить на реальном событии |
| 4 | Формат ack-события источников не наблюдался | `kind='ack'` пока гипотетический | Проверить при появлении реального payload |
| 5 | Пересекаются ли хосты между Zabbix и SolarWinds | Один сервер = две строки в `monitored_objects` | Если пересечение есть — понадобится слой `assets` с маппингом |

| 8 | Нет доступа к TrueConf Server и токена бота | Канал обязателен по кейсу | Адаптер пишется по документации серверного API и проверяется против мок-сервера. Запросить доступ у организаторов; при отказе демонстрировать на моке |
| 9 | Нет доступа к боевому AD | Интеграция обязательна по кейсу | Адаптер проверяется против OpenLDAP в контейнере с воспроизведённой структурой групп |
| 10 | Ставка часа L1 и модель ФОТ для расчёта эффектов | Точность экономического обоснования | Расчёт ведётся от заявленных в кейсе 1,1 млн ₽/квартал, допущения выписаны явно в `economics.md` |

### Приёмка

Прототип считается готовым, когда:
- Реальное событие Zabbix доходит до инбокса дежурного за ≤ 5 с
- Повторы того же события в окне подавления не порождают новых уведомлений
- Обязательная подписка не снимается пользователем, добровольная снимается
- Вход выполняется учётной записью каталога, роли приходят из групп
- Отключение учётки в каталоге прекращает доставку уведомлений
- Уведомление доходит до TrueConf
- Новый источник подключён без единой строки кода — через реестр и маппинг
- Административный дашборд показывает коэффициент дедупликации и процент
  доставки за период
- Тысяча событий из генератора обработана без потерь
- В логах нет ни адресов доставки, ни тел уведомлений, ни payload
