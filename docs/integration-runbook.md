# Раннбук: подключение боевых Zabbix и SolarWinds

Документ для агента, который продолжает работу по подключению реальных
источников. Он самодостаточен: контекст, доступы, текущее состояние, порядок
шагов и критерии приёмки. Инструкции по настройке самих систем вынесены в
`deploy/integrations/README.md` — здесь порядок работ и то, что уже сделано.

Перед началом прочитай `AGENTS.md` (границы MVP, требования ИБ и ПДн) и
`CLAUDE.md` (соглашения). Их требования соблюдаются буквально.

## 1. Что нужно получить

События из боевых Zabbix 7 и SolarWinds Observability Self-Hosted должны
доходить до apollo, превращаться в инциденты и закрываться при восстановлении.
Задача целиком про конфигурацию и проверку: приём, адаптеры и реестр
источников уже написаны и покрыты тестами.

**Готово в коде, менять не требуется:**

- `POST /api/v1/ingest/{source}` — приём, один INSERT в `raw_events`, ответ 202.
  Аутентификация: `X-Webhook-Token`, опционально `X-Webhook-Signature`
  (HMAC-SHA256 hex от тела). Реализация — `backend/app/services/ingest.py`.
- Адаптеры `backend/app/adapters/sources/zabbix.py` и `solarwinds.py`.
- Реестр источников с токенами, часовым поясом, картой критичности и списком
  разрешённых адресов — админка «Источники».

**Подготовлено для этой задачи:**

| Файл | Назначение |
|---|---|
| `tools/tunnel.ps1` | обратный SSH-туннель с автоперезапуском |
| `deploy/integrations/zabbix7-webhook.js` | скрипт media type для Zabbix 7 |
| `deploy/integrations/solarwinds-alert-body.json` | тело Trigger Action |
| `deploy/integrations/solarwinds-reset-body.json` | тело Reset Action |
| `deploy/integrations/README.md` | пошаговая настройка обеих систем |

## 2. Топология и почему именно так

apollo пока работает на рабочей машине Александра (Docker, `deploy/`, наружу
опубликован порт 80). ВМ мониторинга находятся в другой сети и достучаться до
`localhost` не могут, поэтому события идут через **обратный SSH-туннель**:
с рабочей машины на ВМ поднимается порт `18080`, слушающий только петлю ВМ.

```
Zabbix 7 (Linux, 90.156.212.194)     ──► 127.0.0.1:18080 ─┐
                                                          ├─ обратный SSH ─► apollo :80
SolarWinds (Windows, 83.166.251.15)  ──► 127.0.0.1:18080 ─┘
```

Наружу на ВМ ничего не открывается, `GatewayPorts` менять не нужно. При
переезде apollo на выделенную ВМ туннели убираются, а в настройках источников
меняется только URL — скрипт и шаблоны тел остаются прежними.

Альтернатива на случай, если SSH окажется недоступен, — pull-режим, когда
apollo сам опрашивает API Zabbix (`problem.get`) и SWIS. Воркера опроса сейчас
нет, это отдельная работа; браться за неё только если push действительно
невозможен.

## 3. Доступы

| Что | Адрес | Пользователь | Ключ |
|---|---|---|---|
| SolarWinds, Windows Server | `83.166.251.15` | `Admin` | пароль у Александра; ключ `~/.ssh/apollo_tunnel` |
| Zabbix 7, Ubuntu | `90.156.212.194` | `ubuntu` | `local/1.pem` |
| ВМ с языковой моделью | `212.233.74.7` | `ubuntu` | `local/1.pem` (к задаче не относится) |

Пароли в этот файл и в репозиторий не выносятся. Пароль от Windows-сервера
нужен ровно один раз — чтобы положить публичный ключ; дальше вход по ключу.
Ввод пароля интерактивный, агент это сделать не может: попроси Александра
выполнить вход самому (в Claude Code — командой с префиксом `!`).

## 4. Текущее состояние

**SolarWinds (Windows, 83.166.251.15)**

- SSH на порту 22 доступен, значит OpenSSH Server установлен.
- Локально создан ключ `~/.ssh/apollo_tunnel` (ed25519, без пароля).
  Публичная часть:
  `ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIO4UoxpKLOCvhmPx9jbMtuMVIm0NpcvqJmSFv4RLh8Yf apollo-tunnel`
- **Ключ на сервер ещё не установлен.** Это ближайший шаг, выполняет Александр.
  `Admin` состоит в администраторах, а для них Windows-версия OpenSSH читает
  не `~/.ssh/authorized_keys`, а `C:\ProgramData\ssh\administrators_authorized_keys`
  с правами только для `Administrators` и `SYSTEM` — иначе вход по ключу молча
  не работает:

  ```powershell
  $key  = 'ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIO4UoxpKLOCvhmPx9jbMtuMVIm0NpcvqJmSFv4RLh8Yf apollo-tunnel'
  $file = 'C:\ProgramData\ssh\administrators_authorized_keys'
  Add-Content -Path $file -Value $key
  icacls $file /inheritance:r /grant 'Administrators:F' /grant 'SYSTEM:F'
  ```

**Zabbix (Ubuntu, 90.156.212.194)**

- Порт 22 отвечает, версия сервера OpenSSH 9.6p1 (Ubuntu).
- **Подключение с `local/1.pem` под `ubuntu` не проходит:** соединение рвётся сразу
  после обмена версиями протокола (`Connection closed by 90.156.212.194 port 22`),
  до стадии аутентификации. Это не «ключ не подошёл» — при неподходящем ключе
  ответ был бы `Permission denied`.

  Вероятные причины, в порядке проверки:
  1. на ВМ другой ключ (`local/1.pem` заводился под ВМ с моделью);
  2. `sshd_config` ограничивает вход (`AllowUsers`, `Match Address`);
  3. клиентский ключ RSA/SHA-1 отклоняется сервером — проверить, предлагает ли
     клиент `rsa-sha2-256/512`;
  4. срабатывает fail2ban или фильтрация на стороне провайдера.

  Диагностику начинать с `ssh -vv`; если доступ к консоли ВМ есть — смотреть
  `journalctl -u ssh` в момент попытки.

## 5. Порядок работ

Шаги идут строго по очереди: каждый следующий проверяется только после
приёмки предыдущего.

### Шаг 1. Туннель до SolarWinds

```powershell
.\tools\tunnel.ps1 -VmHost 83.166.251.15 -User Admin -KeyFile $env:USERPROFILE\.ssh\apollo_tunnel
```

**Приёмка:** на сервере `curl http://127.0.0.1:18080/health` возвращает 200.

### Шаг 2. Туннель до Zabbix

Сначала разобраться с обрывом SSH (раздел 4), затем:

```powershell
.\tools\tunnel.ps1 -VmHost 90.156.212.194 -User ubuntu -KeyFile .\local\1.pem
```

**Приёмка:** та же проверка `/health` со стороны ВМ.

### Шаг 3. Токены источников

Выдать в админке: «Источники» → «Токен» (или «Токен + HMAC»). Значение
показывается один раз. Токены у источников разные.

**Приёмка:** запрос без токена получает 401, с токеном — 202.

### Шаг 4. Разбор реальных событий до боевого включения

Снять с каждой системы по одному настоящему событию — проблему и закрытие — и
прогнать через «Источники» → «Тест». Эндпоинт разбирает payload и показывает
результат, ничего не записывая в базу.

**Приёмка:** для каждого события определились объект, правило, критичность и
вид (`problem` / `resolved`); тестовый разбор не вернул ошибку.

Если разбор не удался — сначала попробовать декларативный маппинг в реестре
источников и только потом трогать адаптер. Добавлять `if` в ядро нельзя
(`AGENTS.md`).

### Шаг 5. Боевое включение

Zabbix: media type + trigger action с **recovery operation**.
SolarWinds: Trigger Action + **Reset Action**.
Детали и таблица параметров — `deploy/integrations/README.md`.

**Приёмка сквозного пути:** реальная проблема появляется в списке инцидентов,
уведомление приходит в инбокс, а восстановление закрывает **тот же** инцидент,
а не создаёт новый.

## 6. Открытый вопрос, который закрывается этой задачей

В `backend/app/adapters/sources/solarwinds.py` формат закрывающего события —
непроверенная гипотеза: `resolved` определяется по `eventType` из набора
`reset` / `resolved` / `cleared` / `recovery`. Живого закрытия алерта на стенде
никто не наблюдал (в коде стоит `TODO` со ссылкой на открытый вопрос в
`docs/tz.md`).

Первое настоящее срабатывание Reset Action либо подтверждает гипотезу, либо
адаптер правится по факту — вместе с тестом на реальном payload и снятием
`TODO`. Это единственное место во всём конвейере, где остаётся допущение.

## 7. Ограничения

- Ядро не трогать: новый источник — это адаптер или декларативный маппинг в
  реестре, а не условие в общем коде.
- Зависимости сверх перечисленных в `AGENTS.md` не добавлять.
- ПДн: в логи не должны попадать адреса доставки, тела уведомлений и payload
  событий. При отладке интеграций не логировать содержимое вебхуков.
- Секреты (токены, пароли, HMAC) — только в `.env` и в базе, в репозиторий не
  коммитятся. `.env` уже в `.gitignore`.
- Любое расхождение задачи с `AGENTS.md` — остановиться и спросить.

## 8. Что проверить, если события не доходят

| Симптом | Причина |
|---|---|
| `401` от apollo | токен не совпадает; при «Токен + HMAC» не задан секрет подписи |
| `403` | у источника заполнен список разрешённых адресов, а через туннель запрос приходит с `127.0.0.1` |
| `202`, но инцидента нет | событие лежит в `raw_events` с `process_error` — смотреть ошибку разбора |
| Инциденты не закрываются | нет recovery-операции (Zabbix) или Reset Action (SolarWinds) |
| Вместо закрытия новый инцидент | в Zabbix в поле `event_id` подставлен `{EVENT.RECOVERY.ID}` вместо `{EVENT.ID}` |
| Время смещено на часы | часовой пояс источника в реестре не совпадает с временем ВМ; проверить NTP |

Полезные команды:

```bash
docker compose -f deploy/docker-compose.yml logs -f backend normalizer
docker compose -f deploy/docker-compose.yml exec db psql -U apollo -d apollo \
  -c "select id, source, received_at, process_error from raw_events order by id desc limit 10;"
```
