# Развёртывание и эксплуатация

Два контура из одних и тех же файлов: базовый `deploy/docker-compose.yml` —
продовый по умолчанию, `deploy/docker-compose.dev.yml` — оверлей для
разработки. Оверлей применяется только явно; всё, что нужно лишь на деве
(моки, публикация порта БД, демо-кнопки входа), живёт в нём и в прод не
попадает по построению.

Публичный стенд из двух узлов (приложение на VPS, БД на отдельной машине,
связь по закрытой оверлейной сети) описан в [`topology.md`](topology.md) §7:
файлы `docker-compose.app-node.yml` и `docker-compose.db-node.yml`.

## Состав сервисов

| Сервис | Роль | Контур |
|---|---|---|
| `db` | PostgreSQL 16 | оба |
| `backend` | FastAPI: API и приём вебхуков; 2 реплики | оба |
| `normalizer` | разбор raw_events → инциденты; 2 реплики | оба |
| `router` | темы → подписчики → notifications | оба |
| `delivery` | доставка: инбокс, email, TrueConf | оба |
| `llm` | сводки инцидентов | оба |
| `frontend` | nginx: статика + прокси `/api`, `/health*` | оба |
| `ldap` | OpenLDAP-подстановка каталога | только dev |
| `mailpit` | SMTP-перехватчик: вместо TrueConf и релея заказчика, интерфейс на `127.0.0.1:8025` | только dev |
| `trueconf` | мок TrueConf с тем же контрактом — закомментирован, канал заменён email | только dev |
| `llm-mock` | мок OpenAI-совместимого API модели; нужен при `LLM_PROVIDER=openai` | только dev |
| `simulator` | эмулятор Zabbix и SolarWinds | только dev, профиль `demo` |

Реплики заданы в `deploy/docker-compose.yml` (`deploy.replicas`) и меняются
на лету: `docker compose up -d --scale backend=3 --scale normalizer=3`.
Балансировка — nginx, механизм и ограничения в `docs/adr/0003-load-balancing.md`;
проверить распределение можно заголовком `X-Upstream-Addr`:

```bash
for i in 1 2 3 4; do curl -sI localhost/health | grep -i x-upstream-addr; done
```

Все контейнеры: non-root, `read_only` + tmpfs, `cap_drop: [ALL]`,
`no-new-privileges`, лимиты CPU/памяти. Наружу опубликован только порт 80
(nginx); порт БД в проде не публикуется.

## Dev

```bash
cp .env.example .env      # заполнить; для дева хватает значений по умолчанию
cd deploy
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build

# Схема и справочники: роли, источники, шкала критичности
docker compose exec backend alembic upgrade head

# Токены приёма вебхуков из .env (INGEST_TOKEN_*) — в реестр источников
docker compose exec backend python -m app.cli sync-tokens

# Аварийный администратор — пароль печатается один раз
docker compose exec backend python -m app.cli create-admin breakglass

# Каталог тем и соответствие групп тестового домена ролям
docker compose exec backend python -m app.seed

# Демо-состояние: пользователи, подписки, инциденты в инбоксе
docker compose exec backend python -m app.demo_seed

curl localhost/health           # живость
curl localhost/health/ready     # готовность: реально проверяет БД
```

Четыре шага после `up` обязательны: миграции создают схему, `sync-tokens`
пускает источники к приёму, `create-admin` даёт единственный способ войти в
свежую систему, `app.seed` — темы, без которых маршрутизатор не найдёт
получателей и уведомления не появятся.

`sync-tokens` идёт от обратного по сравнению с `issue-token`: секрет объявлен
в `.env` заранее, команда лишь кладёт его хеш в реестр. Одно и то же значение
получают и платформа, и отправитель — боевой Zabbix, SolarWinds или эмулятор
стенда, — поэтому переносить секрет между двумя местами не нужно. Для ротации
в бою остаётся `issue-token`: он генерирует новый токен и печатает его один раз.

`app.demo_seed` обязателен только если стенд нужен «с данными»: сам по себе
`app.seed` событий не создаёт, поэтому после чистого `up` инбокс пуст. Команда
заводит четырёх локальных пользователей с разными ролями и каналами и
прогоняет набор инцидентов Zabbix/SolarWinds через настоящие
`process_batch`/`route_batch` — те же функции, что крутят воркеры, а не
отдельную копию логики. Пароли печатаются один раз при создании.

При `AUTH_PROVIDER=ldap` `demo_seed` назначает доменным учёткам подписки с
каналом email: список `DIRECTORY_USERS` (`backend/app/demo_seed.py`) совпадает
с логинами мока каталога (`deploy/ldap/01-structure.ldif`). Учётка должна
уже существовать в платформе — один раз войти или дождаться синхронизации,
иначе шаг пропустит её как «не найден в каталоге».

Обе команды идемпотентны, повторный запуск ничего не дублирует; `--reset`
убирает прежние демо-данные, не трогая заведённое руками. У `demo_seed`
`--reset` не чистит `raw_events`: слой append-only (правило 2 AGENTS.md).

Канал `web` работает всегда. `email` на стенде идёт через `mailpit`
(`SMTP_HOST=mailpit`, порт 1025, без TLS): письма видны на
http://localhost:8025. `trueconf` отключён (боевая ВМ недоступна,
`TRUECONF_BASE_URL` пуст) — его уведомления уходят в `failed`, это видно на
админ-дашборде и объясняется настройкой стенда, а не дефектом доставки. Пустой
`SMTP_HOST` даёт то же самое для email.

Сводки инцидентов на стенде строит шаблонный генератор
(`LLM_PROVIDER=template`): поля и метрики события подставляются в готовые
формулировки, модель и сеть не нужны. Для OpenAI-совместимого endpoint —
`LLM_PROVIDER=openai` (см. `docs/llm-setup.md`).

Если `.env` создан раньше этих правок, значения `SMTP_*` и `LLM_PROVIDER`
нужно перенести из `.env.example` вручную.

Что даёт оверлей:

- **Порт БД** на `127.0.0.1:55432` — против него идут тесты (`pytest` из
  `backend/`).
- **Моки** LDAP, SMTP (mailpit) и LLM (TrueConf закомментирован — см. состав
  сервисов выше). Переключение с мока на реальную систему — смена URL в `.env`, код
  не меняется.
- **Демо-кнопки входа** («Войти как пользователь / администратор») — учётки
  задаются build-аргами только в оверлее. Обычная сборка идёт без них: в
  статике не остаётся ни кнопок, ни паролей.
- **Эмулятор источников** под профилем `demo` — не поднимается обычным `up`,
  см. ниже.

### Эмулятор источников

`simulator` подменяет генераторы событий на ВМ №1 и №2 (`AGENTS.md` §3), пока
к ним нет доступа по SSH (`docs/integration-runbook.md` §4). Отправляет те же
вебхуки, что боевые Zabbix 7 и SolarWinds — формы payload взяты из
`deploy/integrations/`, поэтому проверяется настоящий путь приёма, а не
упрощённый.

Токены эмулятор берёт из `INGEST_TOKEN_*` — тех же переменных, что применяет
в реестр `app.cli sync-tokens`. Отдельно ничего настраивать не нужно:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  --profile demo up -d simulator
```

Фоновый поток идёт с частотой `SIM_INTERVAL_S` (25 секунд — примерно 2-3
события в минуту) и сам чередует новые проблемы, повторы и закрытия. Сюжеты
для показа запускаются по HTTP на `127.0.0.1:18082`: `GET /scenarios` — список,
`POST /scenario/{name}` — проиграть, `GET /state` — счётчики и открытые
проблемы, `POST /pause` и `/resume` — остановить и вернуть поток. Перечень
сценариев — в README.

Парк объектов совпадает с `app.demo_seed`, так что события ложатся в темы из
`app.seed` и не создают вторую инфраструктуру на дашборде. `SIM_AUTOSTART=false`
поднимает сервис на паузе — стенд молчит, пока не позовут.

Нагрузочный прогон эмулятор не заменяет: залп, перцентили и отчёт —
`tools/load_generator.py`.

Внешние ВМ (боевые TrueConf, Samba AD DC, машина с моделью) недоступны, весь
стенд работает на подстановках: каталог — `ldap`, почта — `mailpit`, сводки —
шаблонный генератор. Моки остаются в оверлее для тестов и работы без стендов;
`trueconf` закомментирован там же.

### Аутентификация: каталог или локальные учётки

`AUTH_PROVIDER` определяет не только вход, но и то, откуда берутся адреса
доставки:

| Значение | Вход | Адреса email / TrueConf |
|---|---|---|
| `local` | локальные учётки (`admin`, `duty`) | таблица `user_contacts` |
| `ldap` | учётки каталога; локальные — только если каталог недоступен | атрибуты каталога, в БД не сохраняются |

Важное следствие: **при `AUTH_PROVIDER=ldap` локальные `admin`/`duty` не
пускаются**, пока каталог жив, — это защита, а не сбой (`app/services/login.py`).
Демо-кнопки на экране входа подставляют именно их, поэтому в режиме каталога
они не сработают: заходить нужно доменными учётками.

Боевой AD заказчика (Samba AD DC на удалённой ВМ, общей с TrueConf) сейчас
недоступен — стенд работает против локального мока каталога: сервис `ldap`
(`osixia/openldap`) из dev-оверлея, структура — `deploy/ldap/01-structure.ldif`.
Каталог нужен и backend, и delivery: backend проверяет вход и синхронизирует
роли, delivery в бою достаёт адрес получателя в момент отправки — мок хранит
`mail` (`<логин>@apollo.test`), поэтому email-доставка через каталог
показывается на mailpit; `ipPhone` в моке нет. Если доступ
к каталогу есть только у backend, уведомления падают в `failed` с «не удалось
определить идентификатор получателя».

Соответствие групп каталога ролям платформы живёт в таблице `role_mappings`
(DN группы → код роли) — в каталоге его нет и быть не может: AD не знает про
роли платформы. Пока таблица пуста, первый доменный вход создаёт пользователя
**без ролей**, и в админку не попасть. Задаётся командой:

```bash
docker compose exec backend python -m app.cli map-role \
  "CN=platform-admins,OU=apollo-groups,DC=apollo,DC=test" admin
docker compose exec backend python -m app.cli list-role-mappings
```

Для тестового домена и OpenLDAP-мока эти связи уже входят в `app.seed`.
Синхронизация ролей — кнопкой в админке «Пользователи» или по расписанию
`LDAP_SYNC_INTERVAL_MINUTES`; роли обновляются и при каждом входе.

Локальный администратор (`create-admin`) при работе с каталогом нужен именно
как предохранитель: каталог живёт на отдельной машине, и если он недоступен,
без локальной учётки в систему не войдёт никто.

Пересборка после правок:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build backend frontend
```

Типы фронта после изменения API:

```bash
cd frontend && npm run types:api    # openapi-typescript → types/api.d.ts
```

## Prod

```bash
cp .env.example .env    # заполнить ВСЕ секреты — пустой секрет валит старт
cd deploy
docker compose up -d --build
docker compose exec backend alembic upgrade head
docker compose exec backend python -m app.cli create-admin breakglass
# Роли доменных групп заказчика — по одной команде на группу:
docker compose exec backend python -m app.cli map-role "<DN группы>" admin
```

`app.seed` в проде не запускается: там свои темы и свои DN групп. Темы
создаются на экране «Темы» под учёткой администратора.

Отличия от дева — только отсутствием оверлея: нет моков, порт БД закрыт,
кнопок демо-входа нет. Обязательные значения `.env` описаны в
`.env.example`; ключевые группы:

- `POSTGRES_*`, `DATABASE_URL` — база;
- `AUTH_*` — секрет JWT, время жизни сессий;
- `LDAP_*` — каталог (реальный вместо мока);
- `SMTP_*`, `TRUECONF_*` — каналы доставки;
- `LLM_*` — endpoint модели (см. `docs/llm-setup.md`).

Миграции при старте не выполняются — это отдельный явный шаг после
развёртывания и после каждого обновления образа:

```bash
docker compose exec backend alembic upgrade head
```

`downgrade base` + повторный `upgrade` проходят — это проверяется тестом.

### Что ещё не закрыто для прода

Зафиксировано в плане как шаг 13 (обвязка ИБ), выполняется отдельно:

## Подключение источников мониторинга

Боевые Zabbix 7 и SolarWinds — `deploy/integrations/README.md` (настройка
систем) и `docs/integration-runbook.md` (порядок работ и текущее состояние).

## Эксплуатация

```bash
cd deploy
docker compose ps                        # состояние
docker compose logs -f backend normalizer
docker compose restart normalizer        # безопасно: очередь в БД, событий не теряет
```

Очереди и задержки видны в интерфейсе: «Платформа» (роль admin) — принято
событий, очереди нормализации и доставки, задержки конвейера против нормативов
(вебхук → инцидент ≤ 2 с, событие → инбокс ≤ 5 с по p95).

Первичная диагностика, если события не превращаются в инциденты:

```bash
docker compose exec db psql -U apollo -d apollo \
  -c "select id, source, received_at, process_error from raw_events order by id desc limit 10;"
```

`process_error` заполнен — ошибка разбора: смотреть адаптер или маппинг
источника. Пусто и `processed_at` пуст — событие ждёт нормализатор: смотреть
его логи.

Логи — JSON в stdout (собираются `docker compose logs`). По требованиям ПДн
в них нет адресов доставки, тел уведомлений и payload событий.

## Нагрузка

Генератор и проверка сквозного пути:

```bash
backend/.venv/Scripts/python tools/load_generator.py \
  --base-url http://127.0.0.1 --rate 40 --duration 60 --real \
  --issue-tokens --admin-user admin --admin-password '...'
backend/.venv/Scripts/python tools/check_pipeline.py --minutes 5
```

Флаг `--test` помечает события тестовыми: они не порождают уведомлений и не
попадают в дашборд. Результаты последнего прогона — `docs/load-test-report.md`;
узкое место — нормализатор, лечится репликами сервиса.
