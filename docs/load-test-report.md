# Отчёт о нагрузочной проверке

Дата: 2026-08-11 · шаг 12 плана сборки

Прогон выполнен инструментами `tools/load_generator.py` и `tools/check_pipeline.py`.
Цель — не «показать красивые цифры», а выяснить, какой компонент упирается
первым, до защиты, а не на ней.

## Условия

| Параметр | Значение |
|---|---|
| Окружение | Docker Desktop на Windows, все контейнеры на одной машине |
| Ограничения ресурсов | по 1 CPU и 512 МБ на `db` и `backend`, по 0.5 CPU на воркеры |
| События | 1000 за прогон, три источника: Zabbix, SolarWinds, Prometheus |
| Доля повторов | 90 % (модель шторма: несколько проблем, много повторов) |
| Доля восстановлений | 15 % |
| Режим событий | боевой (`--real`): замеряется весь путь до инбокса |
| Одновременных запросов | 30 |

Тестовый режим (`--test`, по умолчанию) помечает события `is_test`: такие
инциденты не попадают в дашборд и не порождают уведомлений (FR-INC-7),
поэтому для замера сквозного пути он не годится — приёмочный прогон сделан
боевым.

## Что упирается первым

**Нормализатор.** Он обрабатывает события по одному, тратя на каждое несколько
обращений к БД (upsert объекта, поиск инцидента, upsert инцидента, вставка
в ленту, отметка обработки). При тысяче событий это около пяти тысяч запросов,
что и даёт очередь в 7–10 секунд. Подтверждается прямо: три экземпляра
сократили задержку этого участка в восемь раз, а `FOR UPDATE SKIP LOCKED`
позволил это сделать без единой правки кода и без потерь.

**Следующим становится PostgreSQL.** После расшивки нормализатора выросла
задержка доставки: три нормализатора, приём и воркеры делят между собой одно
процессорное ядро, отведённое контейнеру БД. Это ограничение стенда,
а не архитектуры — в контуре заказчика БД живёт на отдельной машине.

## Устойчивость к перезапуску

Во время первого прогона контейнер нормализатора был перезапущен на восьмой
секунде (в середине потока). После завершения:

- необработанных событий — 0;
- ошибок нормализации — 0;
- записей в лентах инцидентов ровно столько же, сколько обработанных событий.

Последняя проверка и есть доказательство: каждое событие даёт ровно одну запись
в ленте, поэтому расхождение означало бы либо потерю, либо повторную обработку.
Ни того, ни другого не произошло — событие считается принятым после записи
в `raw_events`, а пачка разбирается в транзакции, которая при падении просто
откатывается.

## Что исправлено по итогам прогона

1. **Партиции проверялись запросом к каталогу БД на каждое событие.** Добавлен
   кеш подтверждённых партиций в процессе воркера: на потоке в сотни событий
   это были сотни лишних запросов в секунду.
2. **Пул соединений с БД по умолчанию (5 + 10) не выдерживал пик приёма** —
   запросы ждали не базу, а свободное соединение. Увеличен до 20 + 20,
   вынесен в настройки `DB_POOL_SIZE` / `DB_MAX_OVERFLOW`.
3. **Сам генератор искажал замер**: в задержку попадала очередь внутри клиента.
   Добавлен семафор, таймер стартует после получения слота.

## Выводы для защиты

- Заявленные заказчиком 5400 событий в сутки — это 0.06 события в секунду.
  Прогон дал 58–75 событий в секунду, то есть **тысячекратный запас**
  к средней нагрузке.
- Требования по задержкам (вебхук → инцидент ≤ 2 с, инцидент → инбокс ≤ 5 с)
  на штатной нагрузке выполняются: одиночное событие проходит весь путь
  за 3.2 секунды, шторм из 25 событий — с p95 около одной секунды.
- На искусственном пике в 100 событий/с задержки выходят за целевые. Лечится
  двумя штатными средствами: увеличением числа воркеров (проверено) и выносом
  БД на отдельные ресурсы (в контуре заказчика так и есть).
- Потерь и повторной обработки нет ни при какой нагрузке — это свойство
  архитектуры, а не удачного стечения обстоятельств.

## Как повторить

```bash
# прогон (боевые события, шторм с 90 % повторов)
backend/.venv/Scripts/python tools/load_generator.py \
    --total 1000 --rate 100 --dup-ratio 0.9 --resolve-ratio 0.15 \
    --real --issue-tokens --admin-password <пароль>

# проверка результата
backend/.venv/Scripts/python tools/check_pipeline.py --minutes 3 --expected-sent 1000
```
