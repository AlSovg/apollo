## 2. Разбор по критериям

### 2.1. Техническая реализация · вес 0,20

**Что требует кейс:** работающий прототип, а не концепт.

| Закрыто | Чем |
|---|---|
| Модель данных | `db/schema.sql` v2.1, 20 таблиц, 3 представления |
| ТЗ на реализацию | `docs/tz.md` v1.1, функциональные требования FR-* |
| План сборки | `docs/build-prompts.md`, 15 шагов с критериями приёмки |
| Код | **нет** |

**Что делать:** пройти шаги 0–11 `build-prompts.md`. Минимально
демонстрируемый объём — шаги 0–8 (сквозной путь: вебхук → инцидент →
подписка → доставка → сводка).

**Риск:** шаги 5 (LDAP) и 7 (TrueConf) требуют поднятых контейнеров
OpenLDAP и mock-сервера. Если время кончается — они режутся первыми,
но тогда падает критерий 6.

### 2.2. Архитектура и масштабируемость · вес 0,15

**Что требует кейс:** масштабируемость, подключение новых источников без
переработки ядра, отказоустойчивость.

| Закрыто | Чем |
|---|---|
| Слоистая модель событий | 4 слоя: `raw_events` → `monitored_objects` → `incidents` → `incident_events`, `docs/tz.md` §2 |
| Подключение источников без кода | Три уровня `canonical` / `mapping` / `adapter`, реестр `event_sources`, FR-SRC |
| Абстракции точек расширения | `SourceAdapter`, `IdentityProvider`, `ContactResolver`, `NotificationChannel`, `LlmClient` |
| Горизонтальное масштабирование | Очередь `FOR UPDATE SKIP LOCKED`, воркеры без состояния |
| Отказоустойчивость | `docs/tz.md` §4.5, `docs/topology.md` §6: БД на отдельном узле, приложение переживает её потерю; репликация и RPO/RTO — целевая схема (ADR-0004) |
| Обоснование отказа от брокера | `docs/economics.md` §3.3 — 0,06 события/с |

**Что добавить до 5:** показать на демо реальное подключение седьмого
источника через `field_map` за минуту, без перезапуска. Это самый сильный
аргумент по критерию, и он проверяем вживую.

### 2.3. Применение ИИ · вес 0,15

**Что требует кейс:** и реализацию, и описание сценариев с обоснованием
бизнес-ценности — это два отдельных ожидаемых результата.

| Закрыто | Чем |
|---|---|
| Реализуемый сценарий | Саммаризация инцидента, FR-AI-1…7, шаг 8 |
| Границы применения ИИ | `docs/tz.md` §3.7 — три обоснования, почему нормализация детерминированная |
| Каталог сценариев | `docs/tz.md` §3.8 — 6 сценариев: 1 реализован, 5 в статусе «Концепция» |
| Экономика ИИ-модуля | `docs/economics.md` §3.4 — почему 400 тыс ₽ на GPU не тратятся на первом этапе |

**Осознанное решение команды:** в решении только детерминированная
нормализация плюс LLM-саммаризация. Ставка на предсказуемость: в контуре
АСУ ТП цена ошибочной классификации выше выигрыша от автоматизации,
а модель без исторического корпуса всё равно не обучить.

**Как это защищать.** Не оправдываться. Формулировка: «Мы применили ИИ там,
где ошибка стоит дёшево и ценность мгновенна — в изложении инцидента для
человека. И не применили там, где ошибка стоит простоя. Остальные пять
сценариев описаны с условиями, при которых они окупятся». Осознанные
границы применения ИИ — сильная позиция, а не слабая; слабая — это
«прикрутили LLM к маршрутизации, потому что так больше баллов».

**Что добавить до 4:** на демо показать сводку по реальному инциденту
рядом с исходным JSON — контраст читается мгновенно и лучше любых слайдов.

### 2.5. Информационная безопасность · вес 0,10

| Закрыто | Чем |
|---|---|
| Минимизация ПДн | Только `subject_id` (objectGUID) и роли; ФИО, телефон, email не хранятся |
| Резолв контакта на лету | `ContactResolver`, адрес не логируется |
| Замкнутый контур | Локальная LLM, ни одного внешнего вызова |
| Аутентификация источников | Токен + HMAC + IP-allowlist на источник, `event_sources` |
| Аудит | `audit_log`, append-only |
| Жизненный цикл учёток | FR-IDM: деактивация при увольнении, пересчёт подписок при смене роли |
| Секреты | Только `.env.example` с плейсхолдерами, ничего в репозитории |
| Выбор стека под ревью ИБ | Минимум компонентов, всё в контейнерах, нет брокера и кеша |

**Что добавить до 5:** шаг 13 `build-prompts.md` — заголовки безопасности,
rate limiting, прогон зависимостей на уязвимости с приложенным отчётом.
Отчёт сканера на слайде убеждает сильнее списка мер.

**Честная оговорка для защиты:** таблица `user_contacts` содержит ПДн и
существует временно, до перехода на LDAP; после переключения чистится.
Это лучше сказать самим, чем услышать вопросом.

### 2.7. Демонстрация работоспособности · вес 0,10

**Сейчас 0: кода нет.** Единственный критерий, где нельзя ничего добрать
документами.

Сценарий демо (шаг 14 `build-prompts.md`):

1. Генератор шлёт всплеск событий из Zabbix и SolarWinds.
2. Дашборд показывает приём, дедупликацию, коэффициент схлопывания.
3. Инцидент попадает в инбокс подписанного пользователя — за секунды.
4. Рядом с сырым JSON — сводка от локальной LLM.
5. Пользователь подписывается на тему сам; обязательную отключить не может.
6. Админ подключает седьмой источник через `field_map`, без кода.
7. Пользователь деактивируется в LDAP — доставка ему прекращается.

Пункты 6 и 7 отвечают ровно на те требования кейса, которые обычно остаются
словами. Их стоит показать, даже если придётся урезать что-то другое.

**Обязательное:** прогон целиком на записи, до выхода. Живое демо, которое
не завелось, стоит дороже, чем отсутствие живого демо.

## 5. Чего у нас нет и не будет — как отвечать

| Вопрос жюри | Ответ |
|---|---|
| Почему ИИ не классифицирует и не маршрутизирует? | Осознанная граница: детерминированные правила предсказуемы и проверяемы, а корпуса для обучения ещё нет. Сценарии описаны в §3.8 tz.md с условиями окупаемости |
| Почему не Kafka? | 0,06 события в секунду. Брокер добавил бы 4–6 ВМ, компетенции и поверхность атаки, не решая ни одной проблемы. `economics.md` §3.3 |
| Подключены все 7 систем? | В прототипе две, как задано периметром пилота. Остальные подключаются конфигурацией — покажем на демо |
| Работает с реальным TrueConf? | Против mock-сервера по документации протокола: доступа к боевому серверу у команды нет. Адаптер реальный, меняется только адрес |
| Это же персональные данные? | Идентификатор и роли; ФИО, телефон, email не хранятся, адрес резолвится в момент отправки и не логируется. Таблица локальных контактов временная и чистится при переходе на LDAP |
| Частота критичных инцидентов не задана | Верно, это допущение. Поэтому окупаемость посчитана и без этого эффекта — 2,5 года только на ФОТ |
