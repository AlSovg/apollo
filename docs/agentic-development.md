# Агентная разработка: какие файлы в ней участвуют

Проект собран с ИИ-агентом (Claude Code) в роли исполнителя. Чтобы агент,
который не помнит предыдущих сессий, выдавал согласованный результат, весь
контекст вынесен из головы в файлы репозитория. Этот документ — карта таких
файлов: что в них лежит, кто их читает и как они связаны.

История git подтверждает порядок: первый коммит `b9f2c34` — «контекст проекта,
ТЗ и модель данных», то есть до первой строки кода уже были `AGENTS.md`,
`docs/tz.md` и `db/schema.sql`. Коммиты, созданные с участием агента, помечены
трейлером `Co-Authored-By: Claude …`.

## Слои контекста

| Слой | Файл | Что задаёт | Кто читает |
|---|---|---|---|
| 1. Правила игры | [`AGENTS.md`](../AGENTS.md) | домен, стек и обоснование, границы MVP, ПДн, требования ИБ, инварианты конвейера | любой агент, первым делом |
| 2. Специфика инструмента | [`CLAUDE.md`](../CLAUDE.md) | команды сборки и тестов, соглашения по коду; на `AGENTS.md` только ссылается | Claude Code, подхватывает автоматически |
| 3. Что строить | [`docs/tz.md`](tz.md) | FR/NFR, контракт API, канонический формат события, открытые вопросы | агент на каждом шаге |
| 4. Источник истины по данным | [`db/schema.sql`](../db/schema.sql) | схема PostgreSQL с комментариями; модели SQLAlchemy повторяют её один в один | агент на шагах с БД |
| 5. Как строить | [`docs/build-prompts.md`](build-prompts.md) | 15 шагов (0–14), каждый — самостоятельный промпт с критериями приёмки | человек копирует шаг в агента |
| 6. Почему так | [`docs/adr/`](adr/README.md) | архитектурные решения с альтернативами и причинами отказа | агент и рецензент, когда решение хочется пересмотреть |
| 7. Передача работы | [`docs/integration-runbook.md`](integration-runbook.md) | самодостаточное задание для агента, продолжающего подключение боевых источников | новый агент без контекста сессии |
| 8. Происхождение данных | [`backend/tests/fixtures/README.md`](../backend/tests/fixtures/README.md) | откуда взят каждый тестовый payload, что подлинное, что реконструировано | агент и рецензент |

Порядок чтения для нового агента: `AGENTS.md` → `CLAUDE.md` → нужный раздел
`docs/tz.md` → `db/schema.sql` (если задача про данные) → шаг из
`docs/build-prompts.md`.

## Как устроен `AGENTS.md`

Файл написан как контракт, а не как описание проекта. Разделы идут от
«зачем» к «чего нельзя»:

1. **Что строим** (§1) — задача и цифры заказчика, ключевой принцип «сквозной
   путь важнее фич».
2. **Стек и обоснование** (§2) — включая список того, чего в проекте
   быть не должно: Kafka, Redis, внешние LLM, CDN.
3. **Инфраструктура** (§3) — четыре ВМ и известные ограничения стендов.
4. **Доменная модель и глоссарий** (§4) — термины используются буквально:
   в коде, API и разговоре.
5. **ПДн** (§5) и **безопасность** (§7) — жёсткие правила, «не пожелания».
6. **Архитектура обработки** (§6) — конвейер и пять неприкосновенных правил
   (один INSERT на приёме, `raw_events` append-only, upsert инцидентов и т. д.),
   плюс осознанная граница применения ИИ.
7. **Границы MVP** (§8) — три списка: входит, заложено структурно, не входит.
8. **Как здесь принято работать** (§9) и **карта репозитория** (§10).

Приёмы, которые делают файл пригодным для агента:

- **Запреты сформулированы явно** и с причиной — агенту не нужно угадывать,
  можно ли «на минутку» добавить Redis.
- **Границы MVP разделены на три класса**: реализовано, заложено в схеме,
  не входит. Агент не достраивает «заложенное» по собственной инициативе.
- **Правило остановки:** если задача противоречит `AGENTS.md`, агент
  останавливается и сообщает об этом, а не выбирает сам. Оно продублировано
  в `CLAUDE.md` и в преамбуле каждого промпта сборки.

## Как устроен `CLAUDE.md`

Не дублирует `AGENTS.md`, а дополняет его тем, что нужно именно Claude Code:
целевые команды (`docker compose`, `alembic`, `pytest`, `ruff`, `mypy`,
`npm run generate`), выжимка инвариантов конвейера, соглашения по коду
(`Mapped[...]` вместо `Column()`, Pydantic с `extra="forbid"`, язык
комментариев) и пометка «сначала прочитай `AGENTS.md`». Такое разделение
позволяет использовать `AGENTS.md` и с другими агентами, не переписывая его.

## Как устроен `docs/build-prompts.md`

Файл — пошаговый план генерации приложения:

- **Общая преамбула**, которую подставляют в начало каждого промпта, потому
  что агент не помнит предыдущих шагов: прочитать `AGENTS.md`, `docs/tz.md`
  и `db/schema.sql`, соблюдать их буквально, не добавлять зависимости, при
  конфликте остановиться.
- **Карта шагов 0–14**: каркас → схема и миграции → приём вебхуков → адаптеры →
  нормализатор → пользователи и LDAP → темы и подписки → маршрутизация и
  доставка → LLM-сводки → реестр источников → админ-дашборд → фронтенд →
  генератор нагрузки → обвязка ИБ → демо.
- **Единый формат шага:** что реализовать, ограничения, тесты и блок
  «Приёмка» с проверяемым критерием. Пример: шаг 2 заканчивается требованием
  «POST фикстуры → 202, строка в `raw_events`, payload совпадает
  байт-в-байт».
- **Жёсткий порядок:** шаги 1–7 выстраивают сквозной путь, пока он не
  работает целиком, шаги 8+ не начинаются. Шаг, не прошедший приёмку, не
  считается сделанным.
- **Раздел «Что осталось неопределённым»** — девять вопросов, которые надо
  закрыть опытным путём на стендах, с указанием, на какой шаг они влияют.

## Как агент проверяется

Соблюдение контекста проверяется не доверием, а механически:

- критерии приёмки каждого шага выполнимы командой;
- `ruff`, `mypy` (strict) и `pytest` — см. «Проверки качества» в
  [`README.md`](../README.md);
- нагрузочный прогон и сквозная проверка — `tools/load_generator.py`,
  `tools/check_pipeline.py`, результат — [`load-test-report.md`](load-test-report.md);
- решения, отступающие от базового плана (очередь в PostgreSQL, балансировка,
  оркестрация), зафиксированы в ADR, а не растворены в коде.

## Чего нет в репозитории намеренно

| Файл | Почему не в git |
|---|---|
| `local/ФАЙЛИК ДЛЯ САШИ.md` | реквизиты доступа к стендам; на него ссылаются `AGENTS.md` §3 и README фикстур, но вся папка `local/` в `.gitignore` |
| `local/trueconf_checkup.md` | чекап состояния TrueConf-сервера с реквизитами доступа |
| `local/1.pem`, `local/1.ppk` | SSH-ключи ВМ |
| `.env` | секреты приложения; в репозитории только `.env.example` с плейсхолдерами |
| `.claude/settings.local.json` | локальные настройки агента конкретной машины |
