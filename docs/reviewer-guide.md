# Инструкция для проверяющего

Платформа управления оповещениями Apollo: принимает события мониторинга
(Zabbix, SolarWinds), сводит повторы в инциденты и доставляет уведомления
подписчикам. Стенд работает на двух узлах — приложение на VPS, БД на отдельной
машине ([`topology.md`](topology.md)).

## Доступ

| Что | Значение |
|---|---|
| Адрес | `<APP_URL>` |
| Пароль всех учёток ниже | `<ПАРОЛЬ>` |
| Токен приёма вебхуков Zabbix | `<INGEST_TOKEN_ZABBIX>` |

Значения в угловых скобках передаются вместе со ссылкой на стенд.

| Логин | Роль | Что увидит |
|---|---|---|
| `duty.engineer` | инженер | инбокс, подписки, инциденты |
| `shift.lead` | инженер | то же, другой набор подписок |
| `noc.viewer` | наблюдатель | только просмотр |
| `breakglass` | администратор | всё выше + источники, темы, пользователи, аудит, дашборд |

## Основной сценарий (5–7 минут)

**1. Вход и инбокс.** Откройте `<APP_URL>`, войдите как `duty.engineer`. В
инбоксе уже есть уведомления по демонстрационным инцидентам; новые появляются
сами: эмулятор источников шлёт 2–3 события в минуту.

**2. Инцидент.** Откройте любое уведомление. В карточке инцидента видны объект,
критичность, число повторов события, хронология и сводка. Повторы одной и той
же проблемы не создают новых инцидентов — растёт счётчик (дедупликация по
`(источник, ключ события)`).

**3. Свой сигнал сквозь конвейер.** Проблема, затем восстановление (из корня
репозитория):

```bash
URL=<APP_URL>
TOKEN=<INGEST_TOKEN_ZABBIX>

curl -i -X POST $URL/api/v1/ingest/zabbix \
  -H "X-Webhook-Token: $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @backend/tests/fixtures/zabbix_problem.json
# HTTP/1.1 202 Accepted  {"status":"accepted","raw_event_id":...}
```

В течение нескольких секунд появляется инцидент по хосту `webhook-test-host`;
уведомление получают подписчики подходящей темы (проверьте инбокс и «Подписки»).
Закройте инцидент событием восстановления:

```bash
curl -i -X POST $URL/api/v1/ingest/zabbix \
  -H "X-Webhook-Token: $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @backend/tests/fixtures/zabbix_resolved.json
```

Статус **того же** инцидента меняется на «закрыт», новый не создаётся.

Проверка защиты приёма: без заголовка `X-Webhook-Token` ответ `401`.

**4. Подписки** (`duty.engineer` → «Подписки»). Роль задаёт обязательные темы,
остальные подключаются добровольно: включите тему — уведомления по ней начнут
приходить.

**5. Администрирование** (`breakglass`). «Дашборд» — сводные показатели,
«Источники» — реестр с токенами и настройками разбора, «Темы» — правила
маршрутизации, «Аудит» — журнал действий.

## Что посмотреть по требованиям

| Требование | Где убедиться |
|---|---|
| Доступность по URL | `<APP_URL>/health` → `{"status":"ok"}` |
| БД на отдельном узле | `<APP_URL>/health/ready` → `{"status":"ready"}`: ответ есть только когда backend достучался до БД на другой машине |
| Разделение сервисов | [`topology.md`](topology.md) §1–3 |
| API между компонентами | [`topology.md`](topology.md) §4; схема — `<APP_URL>/api/v1/openapi.json` |
| Схема данных | [`architecture-diagrams.md`](architecture-diagrams.md) §5, [`../db/schema.sql`](../db/schema.sql) |
| Поведение при отказе узла | [`topology.md`](topology.md) §6 |
| Балансировка между репликами | `curl -sI <APP_URL>/health \| grep -i x-upstream-addr` несколько раз — адрес меняется |

## Ограничения стенда

- Боевых Zabbix и SolarWinds нет: события идут от эмулятора и из фикстур.
- Вход — по локальным учётным записям (`AUTH_PROVIDER=local`); интеграция с
  Active Directory реализована и проверена на тестовом каталоге, в этот стенд
  не включена.
- Почта и TrueConf не подключены: доставка идёт в веб-инбокс. Сводки инцидентов
  формируются шаблоном, без языковой модели.
- БД стоит на домашней машине: если она выключена, интерфейс открывается,
  но данные недоступны (`/health/ready` = 503, ответ API — `503`).
