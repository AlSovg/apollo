# ADR-0006. Два узла: БД отдельно от приложения, связь — закрытая оверлейная сеть

Статус: Принята · 2026-09-21

## Контекст

Приёмка требует, чтобы приложение работало на общедоступных серверах, а БД
стояла на **отдельном узле**: «всё в одном контейнере / на одной машине не
засчитывается». Боевых ВМ стенда (`AGENTS.md` §3) в распоряжении нет: доступны
арендованный VPS с публичным адресом и два домашних ПК без публичного адреса.

`AGENTS.md` §7 требует, чтобы БД «не публиковала порт наружу». Когда БД на
другой машине, порт приходится открыть *для соседнего узла*, и вопрос в том,
как это сделать, не открывая его интернету.

## Решение

Два узла, связь между ними — закрытая оверлейная сеть (WireGuard-класса:
Tailscale, ZeroTier).

| Узел | Машина | Что запущено | Файлы |
|---|---|---|---|
| **app** | VPS с публичным адресом | nginx + статика, backend ×2, normalizer ×2, router, delivery, llm | `docker-compose.yml` + `docker-compose.app-node.yml` |
| **db** | домашний ПК | PostgreSQL 16 | `docker-compose.db-node.yml` |

Порт БД защищён четырьмя слоями:

1. Порт публикуется **только на адрес узла в оверлее** (`DB_BIND_ADDR`).
   Без этой переменной compose не запускается, а не публикует порт на все
   интерфейсы. На публичный или домашний интерфейс порт не выходит.
2. ACL оверлея разрешает 5432 только узлу приложения.
3. `pg_hba.conf`: одна БД, один пользователь, `scram-sha-256`, всё прочее —
   `reject`.
4. Публичный трафик приходит только на nginx узла приложения.

Трактовка `AGENTS.md` §7: «наружу» — за пределы закрытого контура. Порт БД
остаётся недоступным из интернета и из любых сетей, кроме оверлея из двух
узлов. Формулировка в `AGENTS.md` уточнена.

Приложение переживает потерю БД (`docs/topology.md`, раздел «Отказы»):
`depends_on: db` в оверлее приложения снят, подключение ограничено 5 с
(`DB_CONNECT_TIMEOUT_S`), приём отвечает `503` + `Retry-After` вместо `500`.

## Альтернативы и почему отклонены

| Вариант | Причина отказа |
|---|---|
| Порт 5432 на публичный адрес + фильтр по IP | Открытый порт БД в интернете нарушает `AGENTS.md` §7 буквально; список IP хрупок |
| SSH-туннель app → db (`ssh -L`) | Работает, но нужен постоянный процесс с автоперезапуском на узле приложения и не даёт ACL; в оверлее это встроено |
| Cloudflare Tunnel для БД | Рассчитан на HTTP; для TCP клиенту нужен `cloudflared access`, лишний процесс в каждом контейнере приложения |
| Приложение дома, БД на VPS (наоборот) | Публичный URL зависит от домашнего канала и туннеля; для приёмки «доступно в любой момент» это хуже, чем БД дома |
| Управляемая БД облачного провайдера | Не доступна в текущем бюджете; по сути та же схема «БД на отдельном узле» |

## Последствия

- Публичная доступность определяется узлом приложения (VPS). Узел БД —
  домашний ПК: если он выключен, интерфейс открывается, но данные недоступны
  (`/health/ready` = 503). На время проверки узел БД должен быть включён.
- Задержка app → db выше, чем внутри одного хоста (оверлей через интернет).
  Приём это не затрагивает: один INSERT, пул соединений; узким местом
  остаётся нормализатор (`docs/load-test-report.md`).
- Для продакшена заказчика схема заменяется: БД и реплика на выделенных ВМ
  в его сети, оверлей не нужен (ADR-0004).
