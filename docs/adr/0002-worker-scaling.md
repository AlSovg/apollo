# ADR-0002. Горизонтальное масштабирование воркеров через SKIP LOCKED

Статус: Принята · 2026-09-07

## Контекст

Требование задания — показать масштабирование, а не только вертикальный
рост ресурсов одного процесса. Нагрузочный прогон (`docs/load-test-report.md`,
прогон 1) выявил первое узкое место: нормализатор обрабатывает события по
одному, p95 «вебхук → инцидент» — 9.26 с при цели 2 с.

## Решение

Каждый воркер (`normalizer`, `router`, `delivery`, `llm`) — stateless-процесс
без разделяемого in-memory состояния. Несколько экземпляров одного воркера
запускаются как реплики одного сервиса и берут работу из одной таблицы через
`SELECT ... FOR UPDATE SKIP LOCKED` — блокировка на уровне строки исключает
обработку одной и той же записи дважды, координатор не нужен.

Масштабирование — штатным средством Compose, без правки кода:

```bash
docker compose up -d --scale normalizer=3 --scale delivery=2
```

Подтверждено прогоном 2 (`docs/load-test-report.md`): три нормализатора вместо
одного — задержка участка «приём → нормализация» падает с p95 10.31 с до 3.30 с,
восьмикратный выигрыш.

## Альтернативы и почему отклонены

| Вариант | Причина отказа |
|---|---|
| Координатор задач (Celery/RQ + брокер) | Требует брокер (см. ADR-0001), лишний компонент; `SKIP LOCKED` даёт ту же гарантию «взял ровно один воркер» без него |
| Партиционирование очереди по воркеру (consistent hashing) | Усложняет ребаланс при изменении числа реплик; `SKIP LOCKED` балансирует нагрузку сам, по факту свободности воркера, а не по заранее вычисленному ключу |
| Вертикальное масштабирование (больше CPU одному процессу) | Нормализатор не параллелит запросы к БД внутри одного процесса без переписывания на asyncio-пул задач; горизонтальный путь дешевле по трудозатратам и уже проверен |

## Последствия

- Число реплик каждого воркера — параметр деплоя, не константа кода.
  Новый источник с более высоким потоком не требует правок воркера.
- Следующее узкое место после расшивки воркеров — сама БД (см. прогон 2:
  задержка доставки выросла, т.к. воркеры и приём стали делить одно ядро
  контейнера `db`). Это ограничение стенда, адресуется ADR-0004.
- Идемпотентность важна сильнее, чем на одном воркере: `incidents` пишется
  через `INSERT ... ON CONFLICT DO UPDATE` по `(source, external_key)`
  (правило 3, `AGENTS.md` §6) именно потому, что несколько нормализаторов
  могут получить события одного инцидента почти одновременно.
