# ADR-0003. Балансировка — nginx + Docker DNS, не выделенный LB

Статус: Принята · 2026-09-07 · уточнена 2026-09-20 (описан фактический механизм)

## Контекст

`backend` (FastAPI) стоит за `nginx`, который раздаёт статику фронта и
проксирует `/api/` (`deploy/nginx.conf`). Требование задания — показать
балансировщик перед приложением, не только перед воркерами.

TLS nginx **пока не терминирует**: TLS и HSTS — шаг 13
`build-prompts.md` (строгая CSP уже настроена). Порт 80 — единственная точка входа.

## Решение

Балансировщик — тот же `nginx`. Реплики `backend` поднимает Docker Compose
(`deploy.replicas` или `--scale backend=N`): все контейнеры доступны во
внутренней сети под одним DNS-именем `backend`, встроенный DNS Docker
(`127.0.0.11`) отдаёт адреса всех живых реплик.

Ключевой момент — **как** nginx получает адреса:

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;
set $backend "backend:8000";
proxy_pass http://$backend;
```

Имя в переменной заставляет nginx резолвить его во время запроса (с кэшем
10 с), а не при старте. Отсюда две вещи:

- реплики, добавленные или пересозданные после старта nginx, подхватываются
  без перезагрузки конфигурации;
- запросы распределяются между адресами из DNS-ответа: резолвер nginx
  ротирует стартовый адрес, а не держит один. Фактическое распределение
  проверяется по заголовку `X-Upstream-Addr` (замер ещё предстоит).

Отказоустойчивость: `proxy_next_upstream error timeout http_502 http_503` с
тремя попытками и потолком 5 с — запрос, попавший на упавшую реплику, уходит
на следующую. Небезопасные методы (POST, PATCH) не повторяются, если запрос
уже отправлен на реплику: вебхук приёма не должен задваиваться из-за обрыва
(если соединение с репликой не установилось, повтор безопасен).

Для проверки балансировки nginx отдаёт заголовок `X-Upstream-Addr` — адрес
реплики, обслужившей запрос.

### Почему не статический `upstream {}`

Открытый nginx резолвит имена внутри `upstream { server backend:8000; }` один
раз при загрузке конфигурации (динамический `resolve` есть только в
коммерческой версии). После пересоздания контейнера или изменения числа
реплик такой блок держит устаревшие адреса и отдаёт 502. Вариант с переменной
и `resolver` ведёт себя корректно при деплое, поэтому выбран он. Цена —
отсутствие активных health-check и весов: их даёт только nginx Plus или
внешний балансировщик.

## Альтернативы и почему отклонены

| Вариант | Причина отказа |
|---|---|
| HAProxy / Traefik отдельным сервисом | Лишний компонент сверх списка в `AGENTS.md` §2 без функциональной необходимости на объёме кейса |
| Kubernetes Service + Ingress | Оверинжиниринг для прототипа и стенда без k8s-кластера; путь тиража, не MVP (см. ADR-0005) |
| DNS round-robin без прокси | Нет повтора на живую реплику — упавшая получает долю трафика до истечения TTL |
| Статический `upstream {}` | См. выше: устаревшие адреса после деплоя |

## Последствия

- `backend` — stateless-сервис: сессии — JWT в httpOnly cookie, состояние не
  хранится в памяти процесса, любая реплика обслуживает любой запрос.
  **Исключение — ограничитель частоты приёма** (`INGEST_RATE_LIMIT_RPS`):
  счётчик живёт в памяти процесса, поэтому при N репликах реальный лимит на
  источник — до N × значения. Для MVP принято; точный лимит потребовал бы
  общего хранилища (счётчик в БД или Redis, последний — вне списка технологий).
- Пассивная проверка здоровья: реплика, не ответившая на запрос, обходится
  через `proxy_next_upstream`. Реплики, не прошедшие compose-healthcheck,
  остаются в DNS, пока контейнер не остановлен.
- Единая точка входа (порт 80) не меняется — клиенты не видят разницы между
  одной репликой и несколькими.
- Число соединений с БД растёт с числом реплик (у каждой свой пул);
  `max_connections` в `deploy/docker-compose.yml` поднят до 200.
