# ADR-0001. Очередь на PostgreSQL, не брокер сообщений

Статус: Принята · 2026-08-10 (ретроактивная запись — решение зафиксировано
в `AGENTS.md` §2 при закладке стека, здесь фиксируется как часть истории
архитектурных решений)

## Контекст

Конвейеру нужна очередь между приёмом вебхука и нормализацией, и между
нормализацией и доставкой. Поток — единицы-десятки событий в минуту
(5400 событий в сутки по условиям кейса).

## Решение

Очередь — таблица в PostgreSQL, воркеры разбирают её через
`FOR UPDATE SKIP LOCKED`. Отдельного брокера (Kafka, RabbitMQ, NATS) нет.

## Альтернативы и почему отклонены

| Вариант | Причина отказа |
|---|---|
| Kafka / RabbitMQ / NATS | Лишний компонент в контуре с требованием ИБ на минимальную поверхность атаки; лишняя точка отказа и лишний узел для оффлайн-сборки из зеркала |
| Redis как очередь | То же самое + at-least-once без транзакционной связки с записью результата (upsert инцидента и снятие из очереди — не одна транзакция) |

## Последствия

- Приём и обработка живут в одной транзакционной модели: событие либо
  зафиксировано и будет обработано, либо не зафиксировано вовсе. Нет окна,
  где событие "потеряно между БД и брокером".
- Верхняя граница пропускной способности — PostgreSQL. На заявленном потоке
  (0.06 события/с) запас на три порядка, подтверждено нагрузочным прогоном
  (`docs/load-test-report.md`): 58–75 событий/с без потерь.
- Ограничение осознанно: при потоке на порядки выше (тысячи событий/с)
  таблица-очередь станет узким местом раньше брокера. Для домена алертов
  такой поток не ожидается ни на пилоте, ни на тираже на всю Группу.
