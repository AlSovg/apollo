# ADR-0005. Оркестрация кластера — Compose/Swarm, не Kubernetes

Статус: Принята · 2026-09-07

## Контекст

Задание требует продемонстрировать кластер, а не только теоретическую
готовность к нему. Стенд — 4 ВМ (`AGENTS.md` §3), срок — семестровая работа
поверх уже сданного прототипа, не отдельный DevOps-проект.

Уточнение 2026-09-20: внешние ВМ недоступны, фактический стенд — один хост с
Docker Compose. Решение от этого не меняется: Compose с `replicas` покрывает
демонстрацию на одном хосте, Swarm остаётся следующим шагом при появлении
нескольких машин.

## Решение

Оркестрация — **Docker Compose с `--scale`** для демонстрации горизонтального
масштабирования на одной ВМ (уже используется, `docs/load-test-report.md`),
и **Docker Swarm** как следующий шаг, когда нужно развести реплики по
нескольким ВМ реально, а не на одном хосте:

- Swarm поднимается поверх тех же `Dockerfile`/`docker-compose.yml` без
  переписывания на другой манифест — `docker stack deploy` читает
  Compose-файл почти без изменений (добавляется секция `deploy.replicas`,
  `deploy.placement`).
- Balancing между узлами делает встроенный Swarm routing mesh —
  дополнительного компонента не требует, тот же принцип, что и ADR-0003.

## Альтернативы и почему отклонены

| Вариант | Причина отказа |
|---|---|
| Kubernetes (k3s/полный k8s) | На стенде из 4 ВМ с уже занятыми ролями (источники, приложение, LLM) разворачивать control plane k8s — трудозатраты, несоразмерные пилоту; каждый новый компонент (etcd, kube-proxy, CNI) — новая поверхность для ИБ-ревью, которого сам k8s-контур ещё не проходил |
| Nomad | Тот же аргумент, что и k8s: новый оркестратор ради оркестратора, когда Compose/Swarm уже покрывают заявленный масштаб (десятки реплик, не сотни) |
| Ручной деплой контейнеров скриптами по ВМ без оркестратора | Не даёт единой команды для пересборки топологии и противоречит самому требованию «кластер», а не «несколько независимых серверов» |

## Последствия

- Переход на Swarm — не смена стека, а следующий шаг того же `docker-compose.yml`:
  доказуемо на защите фразой «то же самое, просто на нескольких машинах»,
  без второго инструмента и второй документации по деплою.
- k8s остаётся заявленным как путь тиража на всю Группу (второй этап,
  `AGENTS.md` §1) — там объём и число сервисов оправдывают его сложность;
  для пилота это открытый пункт, не обязательство.
- Ограничение Swarm против k8s — беднее автоскейлинг и меньше готовых
  операторов (например, для Postgres HA). На объёме кейса это не встречный
  аргумент: реплика БД поднимается вручную (ADR-0004), не автоматизацией.
