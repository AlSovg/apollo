# ADR-0004. Масштабирование БД — потоковая репликация, не шардирование

Статус: Принята · 2026-09-07 (реплика — план тиража, не реализована в пилоте)

## Контекст

Нагрузочный прогон (`docs/load-test-report.md`, прогон 2) показал: после
расшивки нормализатора узким местом становится сама БД — воркеры и приём
делят одно ядро, отведённое контейнеру `db` на стенде. `AGENTS.md` §3 уже
называет реплику в потоковой репликации архитектурно заложенной, но не
поднятой — до появления второй машины под пилот.

## Решение

- **Один primary** для записи — весь конвейер пишет (`raw_events`,
  `incidents`, `notifications`) в него; шардирования нет.
- **Read-реплика** в потоковой репликации PostgreSQL — читающая нагрузка
  (дашборд активных инцидентов, админ-панель, отчётность) уходит туда,
  разгружая primary от конкурентных SELECT поверх пишущего потока воркеров.
- Реплика поднимается на отдельной ВМ, когда она появляется у пилота
  (`AGENTS.md` §3); до этого — архитектурный задел, не блокирующий MVP.

## Альтернативы и почему отклонены

| Вариант | Причина отказа |
|---|---|
| Шардирование (Citus, ручное по `source`) | Оверинжиниринг для объёма кейса (5400 событий/сутки — это КБ/с, не ТБ); ломает `FOR UPDATE SKIP LOCKED` через шарды и упрощённую модель транзакций из ADR-0001 |
| NoSQL для `raw_events` (Mongo и т.п.) | Партиционирование и JSONB в PostgreSQL закрывают тот же кейс без второй СУБД в контуре — второй тип хранилища удваивает поверхность атаки и требования ИБ-ревью |
| Вертикальный рост одного инстанса БД | Первое, что делаем на стенде (снять лимит `cpus: "1.0"`), но это не «масштабирование» в смысле требования задания и не даёт отказоустойчивости |

## Последствия

- Read/write split — это выбор на уровне подключения (какой DSN использует
  какой воркер/эндпоинт), не изменение схемы: `db/schema.sql` не меняется.
- Реплика даёт заодно отказоустойчивость (`AGENTS.md` §3, «реплика PostgreSQL
  в потоковой репликации предусмотрена архитектурно») — переключение на неё
  при падении primary держим ручным на пилоте, автоматический failover
  (Patroni/repmgr) — пункт тиража, не MVP.
- Partitioning `raw_events`/`incident_events` по времени (уже в схеме) и
  read-реплика — независимые оси масштабирования, работают вместе:
  партиции держат объём одной таблицы управляемым, реплика — конкурентную
  читающую нагрузку.
